## 2. Wrong claims found in the model

1. **LoRA never reaches a request** (L6d, L8a). `base-serving.check-model` / `openai-serving-models.lookup-lora` accept an adapter name, but no serving entity attaches the `LoRARequest` (`serve/engine/serving.py:194-213`). `scheduler.add-request`/`schedule` have no `max_loras` gate (`scheduler.py:941-951`). `kv-cache-utils.request-block-hasher` adds no LoRA extra keys (`kv_cache_utils.py:578-595`). The worker's `set-active-adapters`, which is modeled, is unreachable from a request.
2. **`openai-serving-completion.create-completion` drops `n`** and every sampling param except `max_tokens`/`output_kind`. The code passes `n=self.n` (`openai/completion/protocol.py:387`). Its request schema also rejects a string `prompt`, which the code accepts (`protocol.py:52-58`). A `/v1/completions` call with n=3 makes one sequence.
3. **Routes answer before the server listens** (L1a). `instrumentator-health.get-health` (and every route) has no notion of the uvicorn listener. Only `launcher.serve-http`, after engine READY, starts serving (`launchers/api_server/entry.py:142-162`).
4. **`output-processor.abort-requests` leaves the ParentRequest behind.** After an n=3 abort, `parent_requests` still holds `chatcmpl-req-l5-00000001`; the code pops it (`output_processor.py:606-612`). Found in L5; it is not in the benchmark steps.
5. **No `WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR`** in `scheduler.add-request` (`request.py:116-117`). Structured-output requests are schedulable at once in the model (L4d).
6. **World**: the `max-cpu-loras` config is the value 1 instead of "None → max_loras" (`config/lora.py:120-121`), so `--max-loras 2` alone leaves a 1-entry CPU cache.
7. Minor: `worker-utils.request-memory` prints bytes where the code prints GiB with `format_gib`. `check-model` skips `resolve_lora` (see L7).

The citation sample (`--cite-sample 12 --seed 3108`) resolved 6144/6144 citations. All 12 sampled claims match their code. A hand check of about 20 behaviors on the touched flows matched the code everywhere except items 1–5: setup-server, request-memory, run-engine-core, proc-manager launch/monitor, mark-dead, output-handler, health, preflight, terminate-if-errored, watchdog, abort-requests, finish-requests, load/unload-lora checks, LRU add/activate.

## 3. Builder findings confirmed or refuted

- `launcher.setup-server`: "bind the socket … before the engine starts": **confirmed**. It refutes the benchmark's L1(a) wording.
- `launcher.terminate-if-errored` ASSUMPTION "a dead engine core also stops the output handler": **confirmed**. mark-dead cancels the output-queue task, the handler gets EngineDeadError and ends (`core_client.py:1220-1221`, `async_llm.py:905-908`), so `is_running` turns false.
- `core-engine-proc-manager.monitor-engine-liveness` ("engine core exited unexpectedly: engine_dead = True, client shutdown"): **confirmed** (`core_client.py:811-823`).
- `max-cpu-loras` summary "None becomes max_loras … so 1": **refuted as a world value**. The rule is right, but the value is frozen and doesn't track `max-loras`.
- No other "docs versus code" notes were found on the entities this group touches.

## 4. Simulator gaps

- No hard gap blocked a case. Every non-pass is a model or world issue.
- Ergonomic gap (L3): mosaic has no process-exit notification, such as a watcher woken when an instance is killed. The model would have to emulate the sentinel with a long-pending call that the kill ends with `peer-killed`. A first-class `on_kill`/sentinel subscription would make process monitors (MPClient, MultiprocExecutor) natural to model.
