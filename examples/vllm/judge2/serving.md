## 2. Wrong claims in the model

1. **Completions ignore most of the request.** `openai-serving-completion.create-completion` sends `sampling_params: {max_tokens, output_kind}` only. `stop`, `stop_token_ids`, `ignore_eos`, `min_tokens`, `logprobs` and `structured_outputs` are dropped (code: `completion/protocol.py:343-410`). `ServingCompletionRequest` has no `max_tokens` default of 16 (S1).
2. **Stop strings** (`incremental-detokenizer.update`): the model matches only inside the newest token's text and always truncates before the match. The code searches `output_text` with a look-back of `len(stop)` (`detokenizer.py:351`), keeps the string when `include_stop_str_in_output` is set (`:365`), and holds back `max(len(stop))-1` characters while streaming (`:87-88`) (S8).
3. **Structured outputs are not connected end to end** (S10, S11). See the S10 row. Also, `to-sampling-params` reads `response_format.json_schema.json_schema`, but the field's wire alias is `schema` (`generate/base/protocol.py:142`), so an OpenAI-shaped request aborts the simulation.
4. **No `max_tokens > max_model_len` check** (`TokenizeParams.__post_init__`, `renderers/params.py:255-267`) (S7a). The completions path maps a validation error raised inside generate to 500 (S7c).
5. `input-processor.process-inputs` applies the min_tokens check unconditionally and cites `input_processor.py:482-487`, which only runs for an unset `max_tokens`. The check that applies when `max_tokens` is set is `SamplingParams._verify_args` (S6b).
6. `exception-handling.create-error-response` drops `error.data.param`, so ErrorResponse has no `param` (S6a).
7. `skip_special_tokens` is carried but has no effect: special-token text shows in content (S9). Responses carry no `stop_reason` (S3, S4), no `logprobs` (S1, S9) and, for completions, no `created` or `total_tokens` (S1).

Correct and well cited: `sched-utils.check-stop` (matches `sched/utils.py` order, including `min_tokens` placement); the sampler's min_tokens masking (`logit_bias.py:94-105`); the stop-string abort path (`output-processor.process-outputs` → `abort-requests-async`); `api-utils.get-max-tokens`; `to-sampling-params` "max_tokens must be at least 1"; the chat SSE generator's order (role, deltas, finish, usage, `[DONE]`); free-on-finish in `update-from-output`.

Citation sample (`--cite-sample 12 --seed 41`): 12 of 12 match the code (async-llm.checkpoint-restore, llm.run-tiling-engine, scheduler-config.verify-max-model-len, custom-ops.scaled-int8-quant, lora-expand-op, serving-scores load_aware_call, among others). In total, 6144 citations resolve. Hand checks of 12 serving citations found the wrong claims above (items 2, 3, 5); the other 9 match.

Coverage of the entry points: `/v1/completions` and `/v1/chat/completions` (JSON and SSE) are modeled by entities with behavior (`openai-serving-completion.*`, `openai-serving-chat.*`), not just cited. Detokenization is covered by `incremental-detokenizer.update`, which models the stop-string check but not byte-level decoding. Logprobs serialization (`renderers/online_derenderer.py:1042-1115`) has no modeling entity.

## 4. Simulator gaps

- **Scale (S7b).** A 131,000-token prompt aborts on the CEL cost limit in `kv-cache-utils.request-block-hasher` (an O(n²) prefix sum over per-token segments), even at `cost_limit` 1e9. The case was run at a scaled `max-model-len` (1072) with the same 72-token room. Raising the cost limit isn't enough here: the run needs either a cheaper stand-in or native list prefix-sum or segment helpers.
- **No way to print a value from `check`.** Failed expectations print only the expression. Values were read through a `{'a':1}[json(x)]` lookup error. A `--dump`, or printing values on failure, would help judges.
- No case here was blocked by a missing simulator feature. Every non-pass step is a model gap.
