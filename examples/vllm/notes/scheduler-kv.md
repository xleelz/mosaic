## 2. Components

- `scheduler` (scheduler.py:84-442; AsyncScheduler async_scheduler.py:14-78) owns the
  **request state**: `requests` (status, num_computed_tokens, output_token_ids,
  num_output_placeholders, block_hashes, priority, arrival_time, ...), plus `waiting`,
  `running`, `finished_req_ids` and `preempted_req_ids`.
  - `schedule` (591-1556) handles the RUNNING requests first: decodes and continuing chunked
    prefills. The token budget comes from `max-num-batched-tokens`, and each request's tokens
    are capped by long_prefill_token_threshold and by max_model_len - 1. If allocation fails,
    the scheduler preempts the last running request (FCFS) or the max (priority, arrival)
    request (priority), and keeps trying until the request fits or it preempted itself. Then,
    **only if nothing was preempted** (899-900), it admits WAITING requests up to
    `max-num-seqs`. Each admission does a prefix-cache lookup, chunks the request to the
    remaining budget and checks the full sequence (`scheduler-reserve-full-isl`). With chunked
    prefill off, a prompt larger than the budget stops admission. Finally it builds the
    `SchedulerOutput`, then advances num_computed_tokens and (async) the output placeholders.
  - `update-from-output` (2026-2424) appends sampled tokens and runs `sched-utils.check-stop`
    (EOS, stop_token_ids, max_tokens or max_model_len). It advances the request's grammar,
    hashes newly full blocks, and (async) caches completed blocks. Stopped requests are freed.
    It skips requests that were aborted mid-step. Partial prefills emit nothing.
  - `preempt-request` (1571-1614), `free-request` (2714-2750), `finish-requests` (2649-2712),
    `reset-prefix-cache` (2840-2883), `make-stats` (2915-2959) and `get-request-counts`.
- `fcfs-request-queue` / `priority-request-queue` (request_queue.py) do the `peek-request`
  ordering. Priority order is Request.__lt__ (request.py:357-367).
- `sched-utils` (sched/utils.py:98-140): `check-stop`.
- `kv-cache-manager` (kv_cache_manager.py) handles `get-computed-blocks` (hit capped at
  num_tokens-1), `allocate-slots` (371-618: full-sequence check, watermark, free-block check,
  adopt hits, allocate, cache full blocks), `free`, `usage`, prefix-cache stats and the
  `reset-prefix-cache`. The UnitaryKVCacheCoordinator hop is folded into it.
- `full-attention-manager` (single_type_kv_cache_manager.py) owns the **block tables**
  (`req_to_blocks`, `num_cached_block`). It finds the longest cache hit, counts the blocks to
  allocate (evictable hits count), adds hit blocks, allocates new blocks, caches blocks, and
  frees blocks in reverse order.
- `block-pool` (block_pool.py) owns the **KV blocks**. It keeps the free queue compactly as
  `free_front` (uncached frees, LIFO) + fresh ids `next_fresh..num_gpu_blocks-1` + `free_tail`
  (cached frees, LRU). Block 0 is the null block. `ref_cnt` lists only counts of 2 or more.
  `block_hash`/`cached` hold the prefix-cache map. Popping a cached block evicts its hash.
- `kv-cache-utils.request-block-hasher` (kv_cache_utils.py:954-998) hashes new full blocks.
- Structured output: `structured-output-manager` (grammar-init, accept-tokens),
  `xgrammar-backend.compile-grammar` (stop tokens become `override_stop_tokens`, 156-164),
  `xgrammar-grammar` (create, accept-tokens, fill-bitmask, is-terminated).
- KV offload: `host-register`, `kv-offload-cpu-gpu-worker.pin-mmap-region` (pins 64 GiB chunks
  and rolls back on failure), `shared-offload-region` (init, create-next-worker-view,
  create-kv-memoryview), `swap-blocks-triton`, `cuda-mem-ops.copy-blocks`, `dma-copy-backend`,
  `disk-backend`, `async-lookup-manager`, `dual-queue-thread-pool`.

## 6. Assumptions (what the code didn't settle)

- **Block hashes.** sha256 chaining is replaced by a readable, prefix-determined string. The
  hash of a block ending at token E is `<segment keys covering [0,min(E,P))>@<min(E,P)>`, plus
  `+<output tokens>` once the block reaches past the prompt. Long prompts can be given compactly
  as `prompt_segments: [{key, num_tokens}]`; equal keys mean equal tokens.
- `arrival_time` defaults to `now` (ms) when null. Seeded fixture requests use 0, 1 and 2, so
  only relative order is meaningful. Engine-core may send seconds, which is fine as long as all
  requests use the same unit.
- `BlockHashToBlockMap` can hold several blocks per hash. The model keeps the first block under
  each hash, and every block still records its own hash.
- The caller-side `running.pop()` of a preemption is folded into `preempt-request`.
- The xgrammar matcher is a library. It is approximated by a JSON-string FSM (quote token id 1,
  which is `"` in both the gpt2 and Llama-3 vocabularies). Stop tokens are allowed only in the
  accepting state; with `override_stop_tokens` they replace the tokenizer EOS.
- Offload worker-side components run in the GPU worker processes. They sit under engine-core
  per the module rule and are not instanced per rank.
- The cudaHostRegister failure is driven by a driver pinnable-memory budget
  (`host-register.pinnable_bytes`). The platform is a choice (`cuda` by default).

## 7. Docs and common knowledge versus code

- People often say "priority scheduling preempts running requests for a new high-priority
  request". In code, preemption happens only when a RUNNING request can't get blocks, and the
  WAITING loop never preempts (scheduler.py:776-845, 899-1400).
- Any preemption in a step skips all waiting admissions in that step (899-900).
- A request whose prompt is fully cached still recomputes its last block, because the hit is
  capped at num_tokens-1 (kv_cache_manager.py:289-300).
- A preempted request is recomputed from scratch (num_computed_tokens=0), but its full blocks
  stay cached. On resume it hits them, so in practice only the last partial block is
  recomputed (scenario `scheduler-kv-preempted-request-resumes-from-prefix-cache`).
- The default `max_num_seqs` / `max_num_batched_tokens` for `vllm serve` on an H100 are
  1024 / 8192, not 256 / 2048.
- Async scheduling is on by default, so a decode is scheduled again before the previous
  step's output is applied.

## 8. Simulator gaps

- `foreach` caps at 1000 items. `find-longest-cache-hit` probes at most 1000 blocks
  (16,000 tokens), so longer prefix hits are truncated (single_type_kv_cache_manager.py:779-786).
- `entry.repeat` does not repeat inside a multi-step scenario step, so busy-loop scenarios list
  the loop flow once per turn.
- A whole-vocab token bitmask can't be represented. `fill-bitmask` reports only the candidate
  token ids it is asked about.

## 9. Known gaps

- Not modeled: KV connectors and P/D (WAITING_FOR_REMOTE_KVS, kv_holding_waiting, deferred
  frees), streaming-input sessions, spec decode (draft tokens, rejections), encoder and
  multimodal budgets, LoRA limits, Mamba / sliding-window / hybrid managers, the
  long_prefill_token_threshold_adaptive option, pause states other than the budget,
  WAITING_FOR_FSM (a grammar not ready yet), KV events, and the tiered/kvcr/p2p offload
  managers beyond the lookup and IO-pool loops.
- Branches no scenario runs:
  - `host-register` XPU op returning false. The boundary stub always returns ok; a fault
    produces an error instead of `False`.
  - `scheduler.reset-prefix-cache` RuntimeError. It needs blocks held by requests waiting for
    remote KV, which aren't modeled, so it can't be reached.
  - The running loop's top-of-loop `break` when the budget is exhausted before the last running
    request. It needs a running order where an earlier request takes the whole budget while
    later running requests remain. That happens after resume reordering, which no scenario
    sets up. The normal path ends the loop by iteration count instead.
