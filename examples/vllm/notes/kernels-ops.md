## 6. Assumptions

- Op latency classes are assigned by name rules (`RULES`/`CLASS_OVERRIDES` in ops.py): token
  (memory-bound 3 passes over [T,H]), gemm (roofline), moe, routing, attention, blockcopy
  (PCIe), collective (ring volume over NVLink), weightprep, query (0 ms).
- Llama-3.1-8B splits into num_layers + 1 = 33 piecewise graphs (one per attention split);
  each is compiled once for the single range [1, max_num_batched_tokens].
- The compiled graph's runtime cost is not modeled here (piecewise-backend.call is 0 ms); the
  forward cost belongs to models-layers.
- `vllm-target-device` stands for "which `_C` was built / current_platform" in wrapper branches.
- IR `supports_args` predicates are abstracted to flags (variance_size, contiguous, ndim,
  approximate, device type).
- A CUDA-graph replay costs the GPU time recorded at capture.

## 7. Code vs common knowledge

- Default deployment does NOT run `_C.rms_norm`: with -O2 (VLLM_COMPILE, inductor) custom ops
  are "none" and the CUDA platform's IR priority for rms_norm is ["native"], so Inductor
  generates the norm (vllm/platforms/cuda.py get_default_ir_op_priority). vllm_c kernels run
  only without codegen (enforce_eager / -O0).
- Fusion passes (norm+quant, act+quant) are off for an unquantized model; all-reduce+RMSNorm
  needs TP>1 on Hopper/Blackwell with FlashInfer.
- AOT compile is on by default (torch 2.13), so a warm start loads the AOT artifact and never
  calls VllmBackend.
- `gptq_shuffle` with an unsupported bit width silently uses the 4-bit kernel (no error).
- Inventory names the quick-reduce namespace `_rocm_C_custom_ar`; the wrappers call
  `torch.ops._C_custom_ar.qr_*` (CONCAT(TORCH_EXTENSION_NAME, _custom_ar) on ROCm).
- The fixtures moved to H100 usage-context defaults (max_num_batched_tokens 8192), so the
  general compile range is [1, 8192].

## 8. Simulator gaps

- **Whole-millisecond latency (fixed by §29, round 5).** Fractional `latency_ms` is now honored and
  `duration_us` is exact; the text below describes the old behavior. Mosaic latency was an integer number of ms, truncated. Nearly
  every single kernel launch is sub-millisecond and rounds to 0: e.g. rms_norm on 16x4096 bf16
  (~5 us), a decode GEMM 16x4096x4096 (~25 us weight read), even a 2048x14336x4096 FP8 GEMM
  (~120 us). Only large shapes show: an LM-head GEMM 2048x128256x8192 bf16 is ~4.3 ms -> 4 ms
  (scenario `kernels-ops-cutlass-scaled-mm-prefill-vs-decode`), swapping 100 x 2 MiB blocks over
  PCIe ~4 ms (`kernels-ops-op-swap-blocks-pcie`). Latencies are not inflated to compensate;
  per-step kernel time must be summed at the models-layers level or the engine needs sub-ms time.
- `parallel`/`foreach` cannot express the PiecewiseCompileInterpreter's interleaving with
  Dynamo; compile is a sequential loop (as in code).
- No tensor data: numeric correctness (assert_close in the oracle tests) is not modeled.
- The IR priority list is a config object; a scenario cannot remove one key from it, only
  replace an op's list.

## 9. Known gaps

- Host-side dispatch is modeled for only a few ops (gptq_shuffle, convert_weight_packed_scale_zp);
  the rest are latency-only kernels.
- Wrappers other than the hand-written ones (scaled_fp8/int8_quant, cutlass_scaled_mm,
  fusedQuantizeMx, onednn_scaled_int8_quant, weak_ref_tensor, accelerator view, vllm_c,
  convert_weight_packed_scale_zp) are a single narrated call; their asserts/platform branches
  are not modeled.
- Fusion passes match pattern names, not FX graphs. The ROCm AITER passes, QK-norm/RoPE/KV
  fusions and attention+quant fusion are not modeled as passes (their ops are).
- AOT artifact invalidation by changed source files, the mega-AOT artifact, and per-rank caches
  under TP>1 are not modeled. Two behavior steps (the "no match" returns of the act-quant and
  all-reduce passes) are not run.
- Scenario count (80) is above the 60 target: 7 opcheck batteries exercise every wrapper and
  otherwise-unreached op once (mirroring tests/kernels opcheck); the rest are branch scenarios.
