## 6. Assumptions

- Latency: kernels this area owns (BF16 GEMM, Triton MoE GEMM, FP8 block GEMM, norms, activation) use a roofline: `max(bytes / HBM BW, flops / peak)`. Times are integer ms, so the forward runs decoder layer 0 in full with `layer_repeat = num_layers`: owned kernels charge all layers at once; calls into other areas (attention backend, rotary op, all-reduce, topk, moe_sum) happen once and `llama-model.forward` waits `(num_layers - 1) * owner_ms` for the rest. In this fragment alone the other areas' stubs take the default 1 ms each, so absolute step times are only meaningful after merge.
- The modeled default kernels: unquantized MoE -> TritonExperts; FP8 kernel choice is a `choice` (default Triton block for 128x128, CUTLASS otherwise) since init_fp8_linear_kernel depends on GPU and installed libraries; GateLinear tier is a `choice` (default ReplicatedLinear).
- Transformers availability of an unknown architecture is a `choice` (`model-registry.try-resolve-transformers.transformers_class`).
- `_normalize_arch` (convert-type suffix matching) is not modeled; exact names only.
- ModelConfig decides `quantization` from the checkpoint; the sim derives it in `initialize-model` from `config['quantization']` or `hf_config.quantization_config.quant_method`, and calls `get_quant_config` there (in code VllmConfig builds quant_config earlier).
- Forward before load fails with `attribute-error` (the runner has no `self.model` before `load_model`).
- The modelinfo cache file is kept as `model-registry` state, not on `local-disk`.
- LoRA GPU slots are created lazily at first activation with `max_loras` entries.

## 7. Docs vs code

- Brief/profile mention DeepSeek MoE; I modeled Mixtral (FusedTopKRouter softmax top-2) as the MoE because DeepSeek adds MLA and grouped top-k; DeepSeek is registry-level. A `moe-runner.forward` scenario with shared experts and sigmoid scoring exercises the DeepSeek-like runner branches.
- `fp8` no longer supports online quantization (Fp8Config refuses non-serialized checkpoints; use `fp8_per_tensor`).

## 8. Simulator gaps

- Sub-millisecond kernel time: latency is integer ms, forcing the representative-layer scheme (llama.py:432-442 loop is not iterated).
- `parallel` branches cannot race on state; the dual-stream LoRA op is a join of two branches.
- Choices replace platform and library detection (kernel priority lists, kernels/linear/__init__.py:726-810).

## 9. Known gaps

- Pipeline parallelism (IntermediateTensors) not modeled; PP=1 only.
- Other loaders (tensorizer, runai, sharded_state, modelexpress) are in the table but not modeled; selecting them yields an invalid dynamic target.
- Multimodal processing (vllm/multimodal) has no inventory entries and is not modeled beyond M-RoPE.
- Unexecuted branch: `lru-cache-lora-model-manager.add-adapter` "already registered" (the worker checks first, so it is unreachable through the worker path).

## Reconciliation round

- Skips: 269 architecture-specific entries (`vllm/models/<arch>/`, plus per-architecture modules in `model_executor/models` and the Transformers-backend MoE) are skipped with `covered_by: component:model-registry`. 31 ROCm, AITER, XPU and CPU entries are skipped as platform-only. The remaining 179 stay unskipped and count as not modeled. Modeled coverage went from 48% (434/913) to 71% (434/613).
- Decision 2: `attention-layer.get-attention-context` passes the runner's `attn_metadata` (in the AttnCommonMetadata shape) through to `flash-attention-impl.forward` and `do-kv-cache-update`. A dummy or profiling batch (`is_profile`) carries no metadata: KV-cache writes are skipped and `profiling_run` is set. When the caller sends no metadata, the model builds a fresh-prefill layout itself (equal requests, consecutive blocks).
- Decision 4: every rank calls `tensor-model-parallel.all-reduce` on its own rank. Integer `layer` keys feed distributed's rendezvous: 0 = embedding, 1 = o_proj, 2 = down_proj or MoE. TP4 scenarios run every rank concurrently (`await: false`).
- Decision 7: `gpu-hbm-bandwidth-gbps` is a boundary copy owned by kernels-ops (3350, H100). `gpu-dense-bf16-tflops` is 989 (H100). `quantization` and `model-impl` are boundary copies owned by config-platform.
- Decision 8: the `custom-ops.*` stubs are kind function and use kernels-ops' request shapes (`topk`, `k`/`n`/`m`, `out_dtype`).
- Decision 9: latencies are fractional milliseconds per launch. Decoder layer 0 runs in full, and the remaining layers are charged as (num_layers - 1) × layer 0's elapsed time, measured with `now`. `duration_ms` is not used because it rounds to whole ms.
- Decision 13: `base-model-loader.load-model` merges the hub's config.json (`hf-hub.download-config`, config-platform's contract) under the caller's partial `hf_config`. This removes the `init` aborts. It also allocates the weights in `gpu-memory` (kind `weights`). Note: the tp1 and tp4 fixtures already seed `gpu-memory.weights_bytes`, so a load on top of them counts the weights twice. That is a fixture issue for the coordinator.
- Decision 10: `models-layers-seed` has Llama-3.1-8B loaded on every rank (plain `llama-for-causal-lm` key), the Mixtral and FP8 hub rows, and the LoRA adapter files. The forward pass reads TP from `config['tensor-parallel-size']`. In `full-tp4-llama-70b` the seeded config is still the 8B one, because plain keys cannot vary by world.
- `peft-helper.from-local-dir` reads the disk entry's parsed `json` field.
- Decision 14: `oracle-build-models-layers-4` translates test_expert_placement_various_sizes through `expert-map-manager.determine-expert-map`, and passes.
