## 6. Assumptions the code didn't settle

- **Utility round trip.** UTILITY messages really wait in the input queue for the busy loop, and the reply comes back on the output socket. Here the input thread runs them at once and the reply is the call's return.
- **Request ids.** `assign_request_id`'s 8 random characters are a run-local sequence number (`-00000001`, ...), so the scheduler stub's example outputs match the first two requests.
- **has_work.** `engine-core-proc.has-work` exposes the scheduler's answer as a choice (`scheduler_has_requests`, default = `scheduler.has_requests()`). Scenarios that need a drained scheduler set it to `idle`: the shutdown exit, pause/sleep completion and drain. This pins another area's answer and stands in for seeding scheduler-kv state, which a stub can't hold. After the merge, those scenarios should seed scheduler-kv's state instead.
- **Detokenizer text.** Detokenized text is `' t<id>'` per token (no tokenizer in this area), and stop strings match against that.
- **No latencies.** My hops carry no latencies (1 ms default). The code gives no numbers, and the forward-pass time belongs to worker-runner.

## 7. Docs or common knowledge vs code

- The common belief that "the step loop schedules, executes, then returns outputs" doesn't hold here. With the deployed async scheduling, outputs lag one step behind scheduling (scenario `engine-core-generate-batch-queue-lag`).
- `vllm serve` defaults to `disable_log_stats=False`, but `LLM()` forces it True, so `LLM.get_metrics()` fails its assertion unless the caller re-enables stats.

## 8. Simulator gaps

- **Busy loop.** Threads and queues (input thread, output thread, client socket task, output handler) are collapsed into synchronous calls. The busy loop is a self-re-emitting timer, and `input_queue.get()` blocking is a 1 ms poll. The cause is that emits are delivered only after their root's call tree, so they can't cross from generate's lane into the loop's.
- **Batch queue.** `step_with_batch_queue` futures are resolved eagerly: execute_model's latency is paid when the batch is scheduled, not when it is popped (`core.py:723-779`).
- **Waiting generators.** `generate()` awaiting its queue is a 1 ms poll bounded at 400 polls. `LLMEngine.step`/`get_output` is the same.
- **Pause completion.** The future for a pending pause never completes the utility reply (`core.py:2101-2103`). The scenario `engine-core-pause-keep-completes-when-idle` shows the callback running instead.

## Reconciliation round

My decisions were 3, 4, 5, 6, 10 and 12.

**What I changed:**
- **Scheduler-kv contracts.** I copied all ten scheduler interfaces from the owner's fragment: `has-requests`, `pause-state`, `set-pause-state`, `reset-encoder-cache`, `shutdown`, a nullable `finish-requests`, `schedule`, `update-from-output`, `add-request` and `reset-prefix-cache`. I also copied `kv-cache-utils.get-kv-cache-configs`. The only additions are `examples`, kept for determinism in isolation.
- **KV block count.** Startup calls `get-kv-cache-configs` with `available_memory` and `bytes_per_block` (`page_size_bytes × num_layers` from the worker's spec), so TP4 with the 70B model is sized correctly. It then sends `initialize-from-config {num_blocks}`.
- **Engine-dead state.** New interface `async-llm.errored` (`async_llm.py:1307-1309`). It reads `async-mp-client.engine_dead`, which ENGINE_CORE_DEAD, a dead engine process or shutdown sets, plus `async-llm.output_handler_done`. `add-request` and `check-health` now use it. Serving-api should seed `async-mp-client: {engine_dead: true}` instead of faulting `async-llm.errored`.
- **Disconnect token.** `async-llm.generate` now takes `cancel_token`, the caller's disconnect token. Its default is `'disconnect-' + request_id`. Cancelling it fails the pending await, and generate aborts the request in the output processor and the engine core. Serving-api should pass its `disconnect-<X-Request-Id>` token.
- **sync-mp-client loop budget.** `get_output` no longer runs 400 polls. Each empty poll runs one busy-loop iteration (`iterations: 1`), up to 64, standing for the engine process that keeps stepping while the client blocks.
- **Seed fixture.** `engine-core-seed`.
- **Boundary copies** of `enable-lora`, `profiler` and `weight-transfer-backend` (config-platform). The real defaults leave LoRA, profiling and weight transfer off, so the scenarios that use them turn them on.
- **Scenarios against scheduler-kv's real state.**
  - These scenarios now add a real request first: `generate-batch-queue-lag`, `generate-sync-step`, `abort-during-step` (the abort is timed during the step) and `tp4-rank-timeout`.
  - These pin the `has-work` choice to `busy` where they need in-flight work: `pause-keep-completes-when-idle`, `add-rejected-in-shutdown`, `shutdown-drain`, `drain-wait` and `sleep-deferred-while-busy`.
  - `weight-version-write-read` now reads the version back through `get_weight_version` only.
- **LoRA adapter path** changed to `/adapters/sql-lora`, the path models-layers seeds.

**Merged failures that remain, and what each waits on:**

## Fix round (after judging)

**Fixes, with code citations:**
- **E6, parallel-sampling.** The n children (`0_<id>`, `1_<id>`) register with one ParentRequest and the parent's single RequestOutputCollector (async_llm.py:543-547, output_processor.py:630-638).
  - `process-outputs` follows `ParentRequest.get_outputs` (parallel_sampling.py:102-128). A finished child leaves `remaining`; the parent output is finished only when no child remains; FINAL_ONLY aggregates the n completions.
  - Each RequestOutput carries one completion per index. `generate` merges them: DELTA outputs append, CUMULATIVE and FINAL_ONLY outputs replace.
- **E5, offline.** A RequestOutput's `request_id` is the external id (output_processor.py:394-413). DELTA outputs carry the new tokens; CUMULATIVE and FINAL_ONLY carry all tokens, and FINAL_ONLY emits nothing until finished (output_processor.py:318-341). `_finish_request` now drops the external-id mapping (output_processor.py:855-862). Sorting by request id and per-prompt SamplingParams lists live in `llm.run-engine` / `llm.add-completion-requests` (vllm/entrypoints/llm.py, owned by serving-api).

Only the reply rank enqueues an output; a non-reply rank logs its exception and sends nothing (multiproc_executor.py:1053-1068). So a failure on rank2 shows up as the 300 s TimeoutError.
- **E4, graceful-shutdown.**
  - `AsyncLLM.shutdown` → `MPClient.shutdown` → `CoreEngineProcManager.shutdown`: SIGTERM, then wait up to the grace for the engine to exit (5 s when `timeout` is None, 0 s for the API server's `shutdown_timeout=0`), then SIGKILL with a `kill` of engine-core-proc (vllm/v1/utils.py:605-660, engine/utils.py:47-67). - **E2.** The busy loop blocks in a channel `receive` on `engine-core-input:<instance>` (core.py:1586-1601). The input thread, the failure callback and the signal handler `put` into that channel. There is no 1 ms poll any more.
