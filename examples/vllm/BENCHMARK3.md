# vLLM 0.32 benchmark 3: a second blind re-measurement of the generated ontology

The builders never see this file. `BENCHMARK.md` and `BENCHMARK2.md` have both been scored and
discussed, so this file measures the next fix round. It has no case in common with either.
It lists well-known behaviors of vllm-project/vllm at v0.32.0 (the V1 engine), each written so
that it can run as a mosaic scenario against the merged ontology (`examples/vllm/vllm.json`).

**Verify each case against the code before scoring it.** Every expectation below cites the v0.32.0
source (`path:line`, relative to the vLLM source root) that it was drafted from, but any of them can
still be wrong for v0.32.0 with the default engine args. Steps marked "judge: confirm" were not fully
traced. A judge first confirms or corrects each step from the code, citing file and line. Only then
is the ontology scored against the corrected expectation. A corrected step keeps its letter; note the
correction next to the score.

**Default world:** `full-tp1-llama-8b`.
- One 80 GB GPU (rank0) serving Llama-3.1-8B-Instruct as `llama-8b`, with `max_model_len` 131072
  (from the HF config) and vocabulary size 128256.
- The default engine args: block size 16, max_num_seqs 128, max_num_batched_tokens 2048, chunked
  prefill on, prefix caching on, policy fcfs, gpu_memory_utilization 0.92, no speculative
  decoding, LoRA off. In this tree, async scheduling is on by default when nothing is incompatible
  (`vllm/config/vllm.py:1585-1644`), and the GPU model runner is the V2 runner under
  `vllm/v1/worker/gpu/` (`vllm/config/vllm.py:703-738`; judge: confirm).
- Other worlds: `full-tp4-llama-70b` (4 GPUs), `full-small-batch-limits`, `full-prefix-caching-off`,
  plus the area fixtures. Some cases need a vision-language world (Qwen2.5-VL-7B-Instruct on one
  80 GB GPU) or a MoE world (for example Qwen3-30B-A3B on the 4-GPU hardware); the case says so.
- Some cases name an engine-arg or environment variant (say `--api-key`, `--data-parallel-size 2`,
  `VLLM_SERVER_DEV_MODE=1`). Select it through the world's inputs or `choices`. If no world can
  express the variant without a model edit, score the steps that depend on it **partial** and name
  the missing knob.

## Scoring

Each case is broken into lettered steps, (a), (b), (c) and so on. Score every step separately,
using this scale:

| Score | Meaning |
|---|---|
| **pass** | The verified outcome **and** the code's path are reproduced: the right processes or ranks, messages and decisions |
| **partial** | The outcome is right, but the path is wrong or incomplete; or the behavior is modeled but can't be driven without an edit (say which) |
| **sim-gap** | The behavior is modeled as well as mosaic allows. Name the missing feature |
| **missing** | The behavior isn't modeled |
| **fail** | The model produces a different outcome |

**Case score (worst step).** A case scores its worst step, in the order
pass > partial > sim-gap > missing > fail. A case with steps (a) pass, (b) partial, (c) pass
scores partial. A case passes only when every step passes.

**Step-level pass count.** Count the steps scored pass, and report it as `passed / total` per group
and overall, next to the case-level counts. This file has 32 cases and 127 steps: `serving` 8 cases
and 33 steps, `scheduling-kv` 8 and 32, `execution-parallel` 8 and 32, `engine-lifecycle` 8 and 30.
The step count shows progress that the worst-step rule hides. It is not a substitute for the case
score.

Write each case's scenario at `judge3/scenarios/<ID>.yaml`, using fixtures, inputs, `choices`,
`faults` and `steps` only. No mocks, and no model edits. Give each step its own expectation, so a
step can be scored from the run's summary or trace.
