## 2. Wrong claims found in the model

1. **The chat route drops most sampling parameters.** `openai-serving-chat.create-chat-completion` (step "engine_client.generate", which cites chat_completion/serving.py:390-404) sends only `max_tokens`, `n` and `temperature`. The code builds them with `request.to_sampling_params(...)` (serving.py:360-363 → protocol.py:715-786), which carries stop, stop_token_ids, top_p, top_k, min_p, penalties, seed, include_stop_str_in_output, output_kind (DELTA when streaming) and more. This is why V7 fails. The `ServingChatCompletionRequest` schema has no `stop` field either.
2. **Server-default sampling params are ignored.** When the body has no temperature, the model uses `1.0`. The code applies `default_sampling_params = model_config.get_diff_sampling_param()` (serving.py:175; protocol.py:721-728). With `generation_config="auto"` (config/model.py:354) these come from the model's generation_config.json, which for Llama-3.1-8B-Instruct sets temperature 0.6 and top_p 0.9. `model-config.get-diff-sampling-param` is a boundary stub with no behavior. So a default chat request takes the wrong sampler path: in the code it runs the temperature and top-p kernels, in the model it runs neither.
3. **Greedy sampling is not deterministic.** `sampler.sample` returns `random(128000)+100` for every row, so temperature 0 is not repeatable (V6). The claim "One token per request" is fine. The token value ignores the GREEDY sampling type that the same interface computes.
4. **Stop-string matching only looks inside the new text.** `incremental-detokenizer.update` tests `new_text.contains(s)` and takes the first stop string in list order. The code searches back across the previous text (`output_text.find(stop_str, 1 - new_char_count - len(stop_str))`), picks the string that **completes earliest** (detokenizer.py:340-363), and drops any tokens generated after it (detokenizer.py:137-147). The model misses stop strings that span token boundaries.
5. **Streaming is built after the fact** (see V2). The cited lines (serving.py:636-760) emit one chunk per engine output, not one per word of the final text, and the finish_reason comes with the last delta (serving.py:764-791), not in a separate empty chunk.
6. **Minor:** `api-utils.get-max-tokens` leaves out `platform_max_tokens`, `override_max_tokens` and the generation-config `max_tokens` fallback (api_utils.py:189-205). With the Llama defaults the result is still remaining-context or the request's value. The `base-renderer.tokenize-prompt` length check leaves out `_text_len_check`, the character-bound pre-check (params.py:377-395). Both give the same 400.

The sampled citations (`--cite-sample 12 --seed 4242`) all resolve and match their claims: thinking-budget-state, custom-ops.top-k-per-row-decode, the sparse_swa metadata build, aux-output-config, the RL start_weight_update route, the custom-allreduce P2P check, async-mp-client BackgroundResources, two torch_bindings ops, the EAGLE next-token kernel and PostGradPassManager. One is loose: the serving-embedding step "ScalingMiddleware refuses while elastic EP scales" cites middleware/register.py:43-47, which only *installs* the middleware.

I also read these behaviors next to their code. They are faithful:
- `sched-utils.check-stop` (utils.py:98-119): the EOS → stop_token_ids → length order is exact;
- `base-serving.check-model` (serving.py:49-84);
- `instrumentator-health.get-health` (health.py:22-33);
- `async-llm.check-health` and `async-llm.errored` (async_llm.py:1089-1092, 1299-1309);
- `chat-completion-full-generator`, where a missing finish_reason gives "stop" (serving.py:1111-1120);
- `with_cancellation` and `listen_for_disconnect` (api_utils.py:36-91).

Entry-point coverage: POST /v1/chat/completions is modeled by `openai-serving-chat.post-v1-chat-completions`, through middleware, with_cancellation, the renderer, generate and the generators. GET /health is modeled by `instrumentator-health.get-health`. Both are substantive behaviors, not stubs that only cite nearby lines.

## 4. Simulator gaps

| Gap | Case |
|---|---|
| No incremental or streamed responses. A call returns once, so an SSE body cannot be sent chunk by chunk while the callee keeps producing (no "yield"). The builders worked around it by awaiting `generate` and synthesizing the chunks. Part of this could be modeled with a collector-draining loop, but chunk delivery to the client and the 200-already-sent semantics cannot be expressed. | V2 (and the with_cancellation versus StreamingResponse detection in V5) |
| No value-level model of logits. Sampled token ids must be synthesized, so determinism needs a deliberate deterministic function. The model could express this (CEL hash of the context); it chose `random`. This is a model choice, not a hard gap. | V6 |
