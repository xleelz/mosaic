# Judge report: execution-parallel (X1–X6)

The model is `examples/vllm/vllm.json`, judged against the vLLM 0.32.0 code at
`/home/lbethay/.cache/mosaic-bench/vllm-0.32.0`. The scenarios are in `judge/scenarios/X1.yaml` … `X6.yaml`.
They run with

```sh
go run ./internal/devtools/check -f examples/vllm/vllm.json -f examples/vllm/judge/scenarios/<X>.yaml --no-mocks --scenario '^bench-' --trace
```

Every scenario asserts both the outcome and the code's path. A failing assertion is the evidence for a
score below pass.

**Deployed configuration** (verified first, because it decides the path for every case):
- `async_scheduling` is unset, so it resolves to **True** (`vllm/config/vllm.py:1585-1644`). The
  busy loop therefore runs `step_with_batch_queue`, not `step`.
- The **V2 model runner** is the default (`vllm/config/vllm.py:703-738`). `execute_model` returns
  None, and `sample_tokens` produces the output.
- TP 1 uses the `uni` executor; TP 4 uses `mp`.
- `cudagraph_mode` is FULL_AND_PIECEWISE.
- `max_cudagraph_capture_size` = min(max_num_seqs·2, 512) = 512 on an H100 (`vllm/config/vllm.py:2354-2363`).

## 2. Wrong claims in the model

1. **`multiproc-executor.collective-rpc`** says "Broadcast to every rank and wait for all replies (join all)" and cites `multiproc_executor.py:425-454`. The cited code sets `response_mqs = (response_mqs[output_rank],)` whenever `unique_reply_rank` is given (lines 425-427), and `execute_model`, `sample_tokens` and `take_draft_token_ids` always give it (341-376). The model ignores `unique_reply_rank` (it even passes `unique_reply_rank: 0` from `multiproc-executor.execute-model`).
2. **`worker-proc.execute-worker-rpc`**: its own summary says "reply … if this rank is the reply rank", but the behavior replies (and turns exceptions into FAILURE replies) on every rank. Code: `multiproc_executor.py:1053-1054, 1062-1064`. As a result, a non-output-rank exception fails the step immediately in the model. In the code it would hang the collective until `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS` (300 s) and surface as `TimeoutError('RPC call to execute_model timed out.')`, `multiproc_executor.py:434-441`.
3. **`kv-cache-utils.get-kv-cache-configs`** cites `kv_cache_utils.py:2531-2680` but drops the capacity check at 2638-2647 (`_check_enough_kv_cache_memory`, 1003-1040). It fails only when the block count is ≤ 0, so an engine that can't fit one `max_model_len` request starts up in the model.
4. **`scheduler.update-from-output`** cites `scheduler.py:2026-2424` but omits the speculative rollback (`num_rejected`, 2110-2128). **`scheduler.schedule`** never emits `scheduled_spec_decode_tokens` or the 1+k decode width (1135-1141, 1372-1375). Neither `post_step` (`core.py:689-696`) nor `update_draft_token_ids` (`scheduler.py:2550`) is modeled.
5. **Seam: runner → attention metadata.** `gpu-model-runner.execute-model` builds FlashAttention metadata (`flash-attention-metadata-builder.build`) but doesn't pass it into `llama-for-causal-lm.forward`. `attention-layer.get-attention-context` therefore takes its fallback, "No runner metadata - every request is a fresh prefill of q tokens in consecutive blocks", on every real (non-profile) forward, X1 included. Decode or mixed batches see a synthetic prefill layout instead of the runner's block table and seq_lens (`attention.py:700-721`).
6. **Seam: long prompts.** `scheduler.add-request` accepts `prompt_segments` (and stores `prompt_token_ids: null`), but `gpu-model-runner.add-requests` requires `prompt_token_ids` and aborts. The token-list form can't exceed roughly 500 tokens because of the CEL cost of `kv-cache-utils.request-block-hasher`. Together, these keep a scenario from driving any batch over ~500 tokens through the engine (X4 had to lower the capture size).

Citation spot-check: 12 random citations (`--cite-sample 12 --seed 61`). 11 support their claim. `qk-norm-rope-kvcache-fusion` cites only line 1 (the license header) and `vllm-xpu-kernels.fp8-bmm` cites a docstring line; both are weak but not wrong. 5417/5417 citations resolve. I also checked 14 citations by hand on the flows these cases touch. These match the code: `engine-core.step` (core.py:657-687), `engine-core.step-with-batch-queue` (697-800), `executor.execute-model` backend selection, `gpu-worker-impl.execute-model` (gpu_worker.py:1300-1360), `gpu-worker-impl.determine-available-memory` formula (633-807), `cuda-graph-manager.init` capture sizes (cudagraph_utils.py:251-390; vllm.py:2354-2363), `cuda-graph-manager.dispatch` (518-548), `multiproc-executor.monitor-workers` (299-333), `engine-core-proc.handle-executor-failed` (core.py:1701-1702), `cuda-communicator` FlashInfer-first all-reduce (cuda_communicator.py:362-396, envs.py:1970) and `gpu-model-runner.sample` (model_runner.py:1592-1677). Claims 1-4 above are the mismatches. The covered entry points (`execute_model`, `sample_tokens`, `determine_available_memory`, the CUDA-graph dispatch, `monitor_workers` and the rejection sampler) are each modeled by an interface with real behavior, not by one that only cites nearby lines.

## 4. Simulator gaps

- **No process-death fault (X5).** Faults can error, delay or hang a call, but they can't kill an instance (make every in-flight and later call to it never return, and fire a liveness watcher). X5 drives the death by calling `multiproc-executor.monitor-workers` directly, standing in for the sentinel firing. The path after that point is faithful.
- **No numeric data semantics (X6).** Rejection sampling's accept/reject and "outputs match the target model" depend on token probabilities. The model must use a `choice` (`rejection-sampler.sample.acceptance`), so output equivalence can't be asserted.
- **CEL cost budget (X4).** A ~520-token `prompt_token_ids` list aborts in `request-block-hasher` (quadratic CEL over per-token segments: "actual cost limit exceeded"). Large-batch behavior (>512 tokens) can't be driven at the deployed capture size. I lowered `max_cudagraph_capture_size` to 16 instead (a legitimate deployment flag), seeding the matching `cuda-graph-manager@rank0.capture_sizes` because `cuda-graph-manager.init` only runs during startup.
- **Self-emitting busy loop (X4, X5).** `engine-core-busy-loop` re-emits its next iteration asynchronously, so a later scenario step can overlap the previous loop's remaining iterations. Steps are not strictly sequential, which makes per-step trace assertions order-sensitive.
