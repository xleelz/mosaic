## 2. Wrong claims in the model

1. **n>1 streams never complete.** `output-processor.add-request` opens a RequestOutputCollector under each child id. `process-outputs` puts child outputs there, and `async-llm.generate` polls the parent id. There is no `ParentRequest.get_outputs` aggregation. In the code, a single queue is shared by all children (async_llm.py:519-548) and outputs are aggregated (parallel_sampling.py:102-128). (E6)
2. **`output-processor.process-outputs` builds RequestOutputs wrongly.** `request_id` is the internal id instead of `external_req_id` (output_processor.py:394-413). `token_ids` is always the step delta, even for FINAL_ONLY/CUMULATIVE (output_processor.py:318-341). It also never removes `external_req_ids` on finish, which `_finish_request` does (output_processor.py:855-862), so the mapping leaks after every finished request (seen in E2 and E6 final state). (E5, E2, E6)
3. **Offline path.** `llm.run-engine`'s step is titled "Sorted by request id" and cites offline.py:638-642, but it returns the outputs unsorted. `llm.add-completion-requests` replaces a per-prompt SamplingParams list with `{}` (`type(input.params) == list ? {} : input.params`), though offline.py:574-586 pairs the params with the prompts. (E5)
4. **TP>1 shutdown.** `multiproc-executor.shutdown` only sets `shutting_down`. The code closes the death pipes, waits for or kills the workers, and each worker runs `worker.shutdown()` (multiproc_executor.py:509-542, 985). (E4)
5. **Shutdown ordering and grace.** `async-llm.shutdown` sends the SIGTERM but omits the process manager's 0 s grace and SIGKILL of the engine-core tree (v1/utils.py:605-660, engine/utils.py:47-67). The API server's SIGTERM handler (launcher.py:249-289), which stops the engine *before* setting `should_exit`, isn't modeled. (E4)
6. Minor: `launcher.setup-server` narrates only the argument validation. The code binds the listen socket there, before the engine starts (launcher.py:394-398). (E1)

Citation spot-check: `--cite-sample 12 --seed 61` resolved all 12, and the claims match the code. Two are weak:
`qk-norm-rope-kvcache-fusion` cites only line 1 (the license header), and `vllm-xpu-kernels.fp8-bmm` cites a docstring line rather than
the op call. I also read 12 behaviors in my flows next to their cited code:
- These match: run-busy-loop, process-input-queue, has-work, handle-shutdown, signal-handler, async-llm.abort, output-processor.abort-requests, engine-core.shutdown and sync-mp-client.get-output (modeled as a poll).
- These don't: llm.run-engine (no sort), llm.add-completion-requests (params dropped) and output-processor.process-outputs (claims 2 and 1).

Coverage: every entry point in this group is modeled by an entity with a substantive behavior: `cli-main.main`/`serve-subcommand.cmd`, `async-llm.from-engine-args`, `engine-core-proc.run-busy-loop`, `async-llm.abort`, `async-llm.shutdown` and `llm.generate`.

## 3. Builder findings (docs versus code)

- engine-core: "with async scheduling, outputs lag one step behind scheduling". **Confirmed**: `step_with_batch_queue` returns no outputs while the queue isn't full (core.py:698-760), as seen in the `bench-e2` trace.
- engine-core: "`LLM()` forces `disable_log_stats=True`, so `get_metrics()` asserts". **Confirmed**: llm.py:226-227 and llm_engine.py:444-446.
- worker-runner: "gpu_memory_utilization defaults to 0.92, not 0.9". **Confirmed**, as in the fixture (cache.py default 0.92, used in E1).
- New, from this judge: the benchmark's E1 ("the executor spawns workers"), E4 ("API server stops first"), E5 ("in-process engine") and E6 ("fan-out in the output processor, sharing the prompt's KV blocks") are each wrong or imprecise for v0.32.0. The corrections are in §1.

## 4. Simulator gaps

- **Blocking queue get across lanes** (E2, also noted by the builders): `input_queue.get()` can't block until another lane enqueues, so the busy loop is a 1 ms re-emitted poll with an iteration budget. A blocking receive (a rendezvous on a queue/channel that wakes on publish) would model it directly.
- **Emit ordering versus process concurrency** (E1): `emit` is delivered after the root call tree, so the engine-core busy loop shows up after `serve_http` returns. In vLLM it runs in its own process from the end of `run_engine_core`. A detached call into another process lane (`await: false` across processes started inside a call) would fix this.
- **Process kill with a grace period** (E4) could be approximated with deadlines. Mosaic has no "kill a lane/instance mid-call" primitive to show a SIGKILL that pre-empts the teardown.
