## 2. Wrong claims in the model

1. **`sampler.apply-sampling-params`.** At `temperature: 0` the greedy token depends on the seed. In the code, greedy is a plain argmax that ignores the seed (`gumbel.py:176-198`). The `sampler.sample` summary says "FlashInfer when eligible", but no step models that path (`sampler.py:300-344`).
2. **`sampling-params.verify`** cites `sampling_params.py:901-945`. It leaves out the spec-decode rejection of min_p and logit_bias (`:1182-1194`), as well as the logit_bias, stop_token_ids and allowed_token_ids checks.
3. **`engine-core.init` and `engine-core.step-with-batch-queue`** size the queue as `async ? 2 : 1`. The code uses `max_concurrent_batches`: PP+1 under async scheduling, PP otherwise (`config/vllm.py:577-587`). **`engine-core-proc.process-engine-step`** picks the step function from `config['async-scheduling']`, not from `batch_queue_size > 1` (`core.py:242-244`), which contradicts its own title.
4. **`engine-core.init`** reads the deployed `async-scheduling`, not the value `vllm-config.resolve-async-scheduling` resolves, so ngram still gets the batch queue.
5. **`attn-utils.get-kv-cache-spec`** takes the page size from the model dtype instead of `kv_cache_torch_dtype` (`attention.py:323-325,645`; `attn_utils.py:139-154`). As a result, **`engine-core.initialize-kv-caches`** ignores `--kv-cache-dtype`.
6. **`mixtral-for-causal-lm.init`.** The title says "TP x DP > 1", but the behavior uses `ep_size = tp`, while the code flattens DP×PCP×TP (`fused_moe/config.py:1189-1236`).
7. **`engine-core-proc.run-engine-core`** cites `core.py:1471-1482` as "Construct the engine". Those lines choose between DPEngineCoreProc and EngineCoreProc by is_moe, and the behavior drops that choice.
8. **`dp-lb-async-mp-client.get-core-engine-for-request`** cites `core_client.py:1642-1697` but leaves out the `waiting*6*max(0, kv-0.5)` KV penalty. **`add-request-async`** cites line 1590 (the FIRST_REQ branch) as `_send_input`.
9. **`dp-engine-core-proc.run-busy-loop`** calls `process-input-queue` and `process-engine-step` without `on:`, so every DP rank reads rank 0's queue.
10. **`model-loader-utils.process-weights-after-loading`** cites `utils.py:192-200` for "KV-cache scales", but models no scales.
11. **`sampler.sample` behavior[8]** aborts on default sampling params from `dp-client-add-request` (`s.logprobs >= 0`: no such overload). The P3-2 run works around it with `logprobs: -1`.
12. Minor: `input-processor.process-inputs` checks the DP rank after the prompt-length checks; the code checks it first. `cuda-graph-manager.init` leaves out the 1024 ceiling on Blackwell (`config/vllm.py:2356-2358,2484`).

**Citations checked and faithful:** `sampler.add-request` (`states.py:41-71`), `gpu-worker-impl.compile-or-warm-up-model` (`gpu_worker.py:961-963`), the graph-memory gate in `gpu-worker-impl.determine-available-memory` (`:700-704`), `vllm-config.resolve-async-scheduling` (`config/vllm.py:1545-1644`), `pp-handler.broadcast` (`pp_utils.py:247-257`), `cuda-graph-manager.dispatch` (`cudagraph_utils.py:518-548`), and the `encoder-cache-manager` interfaces `can-allocate`, `check-and-update-cache` and `free-encoder-input`. Also faithful: `encoder-cache.free-encoder-cache` and `kv-cache-interface.page-size-bytes`. In total, more than 20 citations were checked.

**Entities that model nothing on their entry point:** the `encoder-cache-manager.*` interfaces have no callers anywhere in the model, so the scheduler entry point for encoder inputs is uncovered. The DP client exists, but nothing on the HTTP path reaches it.

## 3. Builder findings

**Confirmed:**
- Async scheduling is on by default, and ngram turns it off with a warning.
- The V2 runner is the default.
- `vllm serve` on an H100 deploys max_num_seqs 1024 and max_num_batched_tokens 8192.
- `dp-sync-interval` is "step 1 and every Nth step".
- `vllm-config.needs-dp-coordinator` is true for internal LB.

**Refuted:**
- The `data-parallel-size` summary says that above 1 the API server uses a DP client. In fact `async-llm` never routes through it.

## 4. Simulator gaps

No case exposed a true simulator gap: every shortfall is in the model, the contract or the world. Two limits are related:
- **Derived config isn't recomputed per scenario (P3-4, P3-6).** Overriding `pipeline-parallel-size` or `enforce-eager` leaves dependent values stale, such as the executor backend `uni` versus `mp` and `cudagraph-mode`. The model has to resolve them in behaviors, and it does so for async scheduling only.
- **`topology` isn't on the judge's allowed list (P3-2, P3-3).** DP ranks need it, as in the builders' own DP scenarios. Missing worlds (MoE, VLM, FP8 checkpoint) are world gaps, not simulator gaps.
