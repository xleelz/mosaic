# vLLM 0.32 benchmark 5: a blind measurement of mechanism coverage

The builders never see this file. `BENCHMARK.md` through `BENCHMARK4.md` have all been scored and
discussed, so this file measures the mechanism round. It has no case in common with them. It lists
behaviors of vllm-project/vllm at v0.32.0 (the V1 engine, with Model Runner V2 as the default GPU
runner), each written so that it can run as a mosaic scenario against the merged ontology
(`examples/vllm/vllm.json`). This round grades whether the model has vLLM's mechanisms end to end:
a request carried through the API server, the engine core, the scheduler and the workers for
pooling and scoring, logprobs, structured output, tool calling, speculative decoding, the KV cache
and its offload tier, LoRA, multimodal processing, parallel startup and metrics. Every step still
states exact observables (values, error texts word for word, counts, ordering, sizes and timing
from config). A step whose outcome is right in kind but wrong in an exact detail it states (a code,
a text, a field, a number, an order) is not a pass.

**Verify each case against the code before scoring it.** Every expectation below cites the v0.32.0
source (`path:line`, relative to the vLLM source root) that it was drafted from, but any of them can
still be wrong for v0.32.0 with the default engine args. Steps marked "judge: confirm" rest on
inference and were not fully traced. A judge first confirms or corrects each step from the code,
citing file and line. Only then is the ontology scored against the corrected expectation. A
corrected step keeps its letter; note the correction next to the score.

## Scoring

Each case is broken into lettered steps, (a), (b), (c) and so on. Score every step separately,
using this scale:

| Score | Meaning |
|---|---|
| **pass** | The verified outcome **and** the code's path are reproduced: the right processes or ranks, messages and decisions, with the exact details the step states |
| **partial** | The outcome is right, but the path is wrong or incomplete, or an exact detail is missing; or the behavior is modeled but can't be driven without an edit (say which) |
| **sim-gap** | The behavior is modeled as well as mosaic allows. Name the missing feature |
| **missing** | The behavior isn't modeled |
| **fail** | The model produces a different outcome, or states an exact detail that contradicts the verified one |

**Case score (worst step).** A case scores its worst step, in the order
pass > partial > sim-gap > missing > fail. A case with steps (a) pass, (b) partial, (c) pass
scores partial. A case passes only when every step passes.

**Step-level pass count.** Count the steps scored pass, and report it as `passed / total` per group
and overall, next to the case-level counts. This file has 32 cases and 144 steps: `serving` 8 cases
and 39 steps, `scheduling-kv` 8 and 37, `execution-parallel` 8 and 34, `engine-lifecycle` 8 and 34.
The step count shows progress that the worst-step rule hides. It is not a substitute for the case
score.

Write each case's scenario at `judge5/scenarios/<ID>.yaml`, using fixtures, inputs, `choices`,
`faults` and `steps` only. No mocks, and no model edits. Give each step its own expectation, so a
step can be scored from the run's summary or trace.

Each case below is one row: **Setup** (world and variant), **Action** (the lettered steps),
**Expected outcome** (one lettered expectation per step) and **Source** (the `path:line` cells each
step was drafted from).
