# vLLM 0.32 benchmark 4: a blind re-measurement for the precision round

The builders never see this file. `BENCHMARK.md`, `BENCHMARK2.md` and `BENCHMARK3.md` have all been
scored and discussed, so this file measures the precision round. It has no case in common with
them. It lists behaviors of vllm-project/vllm at v0.32.0 (the V1 engine), each written so that it
can run as a mosaic scenario against the merged ontology (`examples/vllm/vllm.json`). This round
grades exact observable detail: HTTP codes, error types and message texts word for word, response
fields, defaults as deployed, check order, metric names and labels, and timing semantics. A step
whose outcome is right in kind but wrong in an exact detail it states (a code, a text, a field, a
number, an order) is not a pass.

**Verify each case against the code before scoring it.** Every expectation below cites the v0.32.0
source (`path:line`, relative to the vLLM source root) that it was drafted from, but any of them can
still be wrong for v0.32.0 with the default engine args. Steps marked "judge: confirm" were not fully
traced. A judge first confirms or corrects each step from the code, citing file and line. Only then
is the ontology scored against the corrected expectation. A corrected step keeps its letter; note the
correction next to the score.

**Default world:** `full-tp1-llama-8b`.
- One 80 GB GPU (rank0) serving Llama-3.1-8B-Instruct as `llama-8b`, with `max_model_len` 131072
  (from the HF config) and vocabulary size 128256.
- The default engine args: block size 16, max_num_seqs 128, max_num_batched_tokens 2048, chunked
  prefill on, prefix caching on, policy fcfs, gpu_memory_utilization 0.92, no speculative
  decoding, LoRA off; async scheduling on when nothing is incompatible. The world pins the two
  batch limits; what `vllm serve` picks when they are left unset is itself a case (Q4-1).
- Other worlds: `full-tp4-llama-70b` (4 GPUs), `full-small-batch-limits`, `full-prefix-caching-off`,
  plus the area fixtures.
- Special worlds, named in the cases that need them:
  - `vl-qwen2-vl-7b`: Qwen/Qwen2-VL-7B-Instruct, a vision-language model with image inputs, on one
    80 GB GPU.
  - `fp8-llama-3-8b`: an FP8 checkpoint of Meta-Llama-3-8B-Instruct (for example
    `neuralmagic/Meta-Llama-3-8B-Instruct-FP8`, `quant_method: "fp8"`, static activation scales,
    `max_model_len` 8192), and `fp8-llama-3-8b-kv-fp8`, the same with `--kv-cache-dtype fp8`.
  - `moe-mixtral-8x7b-tp2-ep`: Mixtral-8x7B-Instruct (8 experts, top-2) on 2 GPUs with
    `--tensor-parallel-size 2 --enable-expert-parallel`.
  - A few cases name a variant beyond these (Qwen3-30B-A3B with data parallel, an A100 or V100
    host, 2 GPUs for the VLM). Select it through the world's inputs or `choices`.
- Some cases name an engine-arg or environment variant (say `--kv-events-config`,
  `--enable-server-load-tracking`, `VLLM_SERVER_DEV_MODE=1`). Select it through the world's inputs
  or `choices`. If no world can express the variant without a model edit, score the steps that
  depend on it **partial** and name the missing knob.

## Scoring

Each case is broken into lettered steps, (a), (b), (c) and so on. Score every step separately,
using this scale:

| Score | Meaning |
|---|---|
| **pass** | The verified outcome **and** the code's path are reproduced: the right processes or ranks, messages and decisions, with the exact details the step states |
| **partial** | The outcome is right, but the path is wrong or incomplete, or an exact detail is missing; or the behavior is modeled but can't be driven without an edit (say which) |
| **sim-gap** | The behavior is modeled as well as mosaic allows. Name the missing feature |
| **missing** | The behavior isn't modeled |
| **fail** | The model produces a different outcome, or states an exact detail that contradicts the verified one |

**Case score (worst step).** A case scores its worst step, in the order
pass > partial > sim-gap > missing > fail. A case with steps (a) pass, (b) partial, (c) pass
scores partial. A case passes only when every step passes.

**Step-level pass count.** Count the steps scored pass, and report it as `passed / total` per group
and overall, next to the case-level counts. This file has 32 cases and 136 steps: `serving` 8 cases
and 37 steps, `scheduling-kv` 8 and 31, `execution-parallel` 8 and 35, `engine-lifecycle` 8 and 33.
The step count shows progress that the worst-step rule hides. It is not a substitute for the case
score.

Write each case's scenario at `judge4/scenarios/<ID>.yaml`, using fixtures, inputs, `choices`,
`faults` and `steps` only. No mocks, and no model edits. Give each step its own expectation, so a
step can be scored from the run's summary or trace.
