## 6. Assumptions / what the code did not settle

- Workspace trust and modal prompts are choices on my side (`trust`, `close_confirmation`,
  `confirm`, `prompt`, `task_error`, `allow`, ...) whose defaults follow the boundary answer
  (`trusted` from the stub). Untrusted scenarios use the `untrusted-folder` fixture plus the
  `denied` option, so they also hold after the merge where the owner answers `false`.
- DAP traffic goes straight to `debug-adapter`; in desktop it is relayed through
  MainThreadDebugService/ExtHostDebugService (exthost). Adapter events (`initialized`,
  `stopped` after steps/stopOnEntry, `terminated` after terminate) are emitted by my
  behaviors on the adapter's behalf. js-debug capabilities are constants in the stub response
  (configurationDone, terminate, function breakpoints; no restart).
- Compound launch configurations, variable substitution (`${...}`), dynamic configuration
  providers and debug configuration providers in the extension host are not modeled
  (`resolve-configuration-by-providers` returns the config as is).
- The task terminal's process exit is a choice (`process_exit` zero/nonzero); background tasks stay
  active. Problem matcher marker counts (DebugTaskRunner errorCount) are not modeled; only the
  exit code decides.
- The terminal cwd/executable validation happens on the OS file system, not the `disk` model:
  modeled as a choice on `terminal-process.start`.
- Storage writes that my scenarios must read back (terminal buffer/layout, breakpoints, watch
  expressions, active output channel) live on my own components as stores standing for
  IStorageService workspace keys, not on `storage-db`.
- The workspace id passed to the pty host is the constant `w1-app`.
- Command dispatch: `<feature>-contrib.execute-registered-command` mirrors
  CommandsRegistry.getCommand(id).handler (commands.ts:129) so every command interface is
  flow-reachable; after the merge platform-core's `command-service.execute-command` is the
  real entry.

## 7. Docs/common knowledge vs code

- `task.allowAutomaticTasks` defaults to `off`, yet "off" only blocks automatic tasks when the
  user set it explicitly (`value === 'off' && userValue !== undefined`); with the default the
  user is prompted once (runAutomaticTasks.ts). Modeled per code.
- Closing the last window on Linux/Windows counts as "exit" for terminal revive (onExit):
  buffers are persisted and the layout kept (terminalService.ts:678-693).
- A persistent terminal that was never interacted with is shut down on reload, not kept
  (PersistentTerminalProcess.detach checks the interaction state).
- `debug.startFromConfig` saves before starting (saveBeforeStart defaults to
  `!options?.parentSession`), unlike `workbench.action.debug.start`, which saves itself and then
  passes `false`.

## 8. Simulator gaps

- Steps wait for all timers of the previous step, so a scenario cannot reload a window and
  reconnect within the 60 s grace time (the runner fires first). The reconnect case starts from
  a seeded post-reload pty state (`terminal-reconnect-after-reload`); the expiry case is
  `terminal-grace-time-expires`. (ptyService.ts:812-817, 836-842)
- The heartbeat is a finite timer (`count: 4`), so every heartbeat run ends with the pty host
  declared unresponsive once beats stop; healthy-path scenarios assert on the timers fired while
  beating (`pty-host-heartbeat-healthy`). (heartbeatService.ts, ptyHostService.ts:386-415)
- `@debounce(500)` on `_saveState` is an `after_ms` emit without coalescing several changes.
- `Promise.race([persist, timeout(2000)])` is a `timeout_ms` with `on_error: continue`.
- Dynamic map updates use `merge`/`omit` with `foreach` (no indexed `set`).
- Scenario step `input` cannot set a field to null over fake data; `task-service.run`'s
  TaskNotFound branch is driven through a `default: null` request field.

## 11. Fix round (after judging)

The fragment is edited by a patch script kept outside the repo (`/tmp/tdt/patch.py` + `scen.py`, applied to
the pre-round fragment); the generator under `gen/terminal-debug-tasks/` was not changed this round.

### Fixes
- **T1, pty data streams to the renderer.** `terminal-process.on-process-data` (node-pty onData, flow-control
  pause past `HighWatermarkChars`, terminalProcess.ts:333-348) `yield`s chunks; `pty-service.on-process-data`
  (stream) coalesces them for the 5 ms TerminalDataBufferer window, records them for replay (XtermSerializer) and
  yields `{id, event}` (ptyService.ts:353, 828-833; terminalDataBuffering.ts:28-50);
  `local-terminal-backend.listen-process-data` is the direct proxy listener (localTerminalBackend.ts:152) and calls
  `local-pty.handle-data` -> `terminal-process-manager.on-process-data`, which keeps what xterm was written
  (`terminal-process-manager@w1.procs[id].output`). The stand-in shell writes the prompt `$ ` (assumption).
- **T2, replay.** `pty-service.start` on a started (or revived) process calls `pty-service.trigger-replay`
  (ptyService.ts:883, 889-893, 957-972), which publishes `pty-service.on-process-replay`;
  `local-terminal-backend.on-process-replay` -> `local-pty.handle-replay` (basePty.ts:90-116) writes it back.
  Scenario `terminal-reload-replays-live-buffer` reloads with `restart: workbench-window w1` between detach and
  reattach (at_ms steps) and checks the buffer came back from the pty host and the shell was never killed.
- **T3, pty host exit.** `pty-host-service.on-pty-host-exit` now `restart`s `pty-service` (every pty and the
  PtyService state die with the process), publishes `pty-host-service.pty-host-exit`; `start-pty-host` publishes
  `on-pty-host-start`. The window logs the exit (baseTerminalBackend.ts:46-48), fires onPtyHostRestart when it had
  connected before (:49-59), reconnects its direct proxy (localTerminalBackend.ts:104-108), and each process
  manager (terminalProcessManager.ts:589-617) relaunches normal terminals with the restart message, or reports a
  feature terminal without reconnection properties exited with -1. A kill-fault variant is covered.
- **D1.** `configuration-manager.resolve-configuration-by-providers` calls the new
  `adapter-manager.activate-debuggers` (`onDebugResolve`, `onDebug`, `onDebugResolve:<type>` in parallel,
  debugAdapterManager.ts:488-499; debugConfigurationManager.ts:148-152). `select-configuration` falls back to the
  first configuration (:476-481) and the seed selects "Launch Program", as the constructor does at startup (:85-97).
  `debug-adapter.start-session` / `stop-session` have behavior (debugAdapter.ts:247-362).
- **D2.** New entries `raw-debug-session.on-adapter-exit` / `on-adapter-error` (rawDebugSession.ts:96-107).
  `shutdown(error)` sends disconnect with 200 ms on error (2 s otherwise, :605-606). `fireAdapterExitEvent` attaches
  the error only if `debugAdapterStopped` is still false, i.e. stopping the adapter failed (:619-645), and then
  `debug-service.on-did-end-adapter` shows "Debug adapter process has terminated unexpectedly (...)"
  (debugService.ts:749-753).
- **Oracle: OutputMonitor and TerminalOutputCache.** `output-monitor.start-monitoring` / `wait-for-idle` poll with
  500 ms doubling to 10 s, Idle after 2 quiet polls when not active, Idle at once on a y/n prompt, Timeout at 20 s,

- **Features:** `terminal-create` feature:integrated-terminal, `debug-start-selected` feature:debugging,
