## 6. Assumptions / what the code did not settle
- The default participant is the Copilot Chat extension's agent (`github.copilot.default`, seeded as activated). When Copilot is not installed the real default is ChatSetup's `SetupAgent` (chatSetupProviders.ts:73) which drives setup; not modeled.
- The agent's result (success/error/rate-limited/filtered) is a `choice` on `chat-agent-service.invoke-agent` (`agent_result`), standing in for the extension's IChatAgentResult.errorDetails.
- `run-request` is emitted (async) from send-request, mirroring `_sendRequestAsync` not being awaited by sendRequest. Its sim runs before the next scenario step, so "request in flight" cases seed `pending: true`.
- processNextPendingRequest re-sends through `send-request` (the code calls `_sendRequestAsync` directly, skipping the empty/busy/read-only gates; outcomes are identical for the modeled cases). Steering texts are joined with `\n\n` as in code.
- Slash commands (contributed and agent subcommands), variable resolution, hooks collection, MCP autostart, title generation and the agent-host managed-policy gate in `_sendRequestAsync` are not modeled.
- Tool invocation: the tool's `needs_confirmation` flag stands for "prepareToolInvocation returned confirmationMessages"; autopilot risk gate, preToolUse hooks, post-execution approval and session-level auto-approve levels are not modeled. Internal tools run in-renderer; extension tools go to the extension host.
- accept-deferred: the code saves when `!autoSave || !isDirty`; the dirty check (files-search-scm state) is not read — with auto-save on the model assumes the file is dirty and skips the explicit save.
- reject-deferred for an existing file: the text-model undo is files/editor state and is not modeled; the follow-up model save is approximated with `text-file-service.save {skip_save_participants: true}`.
- Export content is a summary string, not `model.toExport()` JSON; import parsing validity is a `choice` (`content`).
- Inline chat with `chat.inlineChat.agentHost.enabled` records the attempt in ctx and falls back to a local session (the agent-host path belongs to the agents area).

## 7. Docs / common knowledge vs code
- "Enter queues while a request runs": in code the queue/steer default is `chat.requestQueuing.defaultAction` = 'steer' (chat.shared.contribution.ts:1956-1965), and both queueMessage and steerWithMessage send normally when nothing is in progress (chatQueueActions.ts:107-111, 160-164).
- Keeping chat edits explicitly saves the file with `force: true` for manual savers (chatEditingModifiedDocumentEntry.ts:283-295), which users may not expect.
- Global auto-approve requires a one-time opt-in dialog even when the setting is true (languageModelToolsService.ts:1430-1435, _checkGlobalAutoApprove).

## 8. Simulator gaps
- Awaiting a confirmation across user actions: `IChatToolInvocation.awaitConfirmation` blocks inside invokeTool until the user clicks Accept/Skip (chatService.ts:1062-1086). Steps cannot overlap, so the wait is a `choice`; the accept/skip commands are modeled as confirming an already-waiting invocation seeded in state, and a later invoke reusing that call id (as the streaming pending tool call path does, languageModelToolsService.ts:515-521).
- Cancellation racing an in-flight async request: emits run to completion before the next step, so cancel-while-running is driven by seeded state (`pending: true`), not by a real race (chatServiceImpl.ts:2613-2648).
- `raceTimeout(responseCompletePromise, 1000)` after cancel (chatServiceImpl.ts:2645-2647) is not modeled.
- Observable-driven state (autoruns, `transaction`) is flattened into direct state writes (chatEditingSession.ts:467-469).

### Fixes
- **A1 routing.** `chat-widget.accept-input` passes the widget's mode. The default is Agent, which falls back to Edit when `chat.agent.enabled` is off (chatInputPart.ts:936-940, 1205; chatWidget.ts:3562). `chat-service.send-request` resolves `get-default-agent(location, mode ?? ask)` (chatServiceImpl.ts:1643-1646). The new `chat-request-parser.parse-chat-request` finds a leading `@name`: it must come first, be known at the location and support the mode (chatRequestParser.ts:19, 123-170). The new `chat-agent-service.get-agents-by-name` looks names up (chatAgents.ts:524-526). The agent is the silent agent, else the mention, else the default (1652-1653).
- **Participant seed.** The seed now follows extensions/copilot/package.json:1296-1641: default (ask/panel), editingSession (edit), editsAgent (agent), editingSessionEditor, notebook, terminal, plus the non-default vscode and terminalPanel. Modes fall back as in chatParticipant.contribution.ts:318.
- **A1 MCP autostart.** `run-request` calls `mcp-service.autostart` before invoking when the session can use tools. Servers that start become a `mcpServersStarting` progress part (2169-2176).
- **A1 progress.** `chat-agent-service.invoke-agent` calls the extension host with `stream: true` and re-yields each `$handleProgressChunk` chunk (mainThreadChatAgents2.ts:481). `run-request` feeds each chunk to the new `chat-service.accept-response-progress`, which drops chunks after cancellation (1862-1883).

A canceled invoke returns `canceled` without overwriting the response (2211-2212). `chat-service` lost `capacity: 1`: its methods await, which frees the renderer thread, and the old limit queued a cancel behind the running request.
- **A2.** `await-confirmation` gains a `wait` option that blocks on the channel `tool-confirmation:<call>`. `confirm-with` puts to that channel (chatService.ts:1076-1105). The scenario is `lm-tool-invoke-waits-for-accept-command`.
