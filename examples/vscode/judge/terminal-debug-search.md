# Judge report: terminal-debug-search (T1–T3, D1–D2, S1–S2)

Model: `examples/vscode/vscode.json` (merged). Code: `vscode-1.144.0` snapshot. Every case runs from
`full-window`, with no mocks. Scenarios are in `judge/scenarios/{T1,T2,T3,D1,D2,S1,S2}.yaml`. Each case has
one or more passing scenarios for what the model gets right. Scenarios named `*-gap-*` (and

where the model diverges. Totals: 18 scenarios, 10 pass and 8 fail (the expected failures).

## 2. Wrong claims in the model

1. **`search-actions.cmd-search-action-cancel`** says it calls `search-model.clear`, which clears the results. The code cancels the token and keeps the results (searchActionsTopBar.ts:282-286 → searchModel.ts:381-387). `search-model.clear` cites only the class line (searchModel.ts:25), not a method that clears.
2. **`ext-host-debug-service.start-da-session`** says it resolves the debug adapter descriptor from the extension's factory, creates the adapter and starts it. Its behavior only stores `{session_id, type}` under the handle, and `debug-adapter.start-session` is never called. The code throws when there is no descriptor (extHostDebugService.ts:612-616), and that case can't happen in the model. Related: `configuration-manager.resolve-configuration-by-providers` returns the config unchanged and skips `activateDebuggers('onDebugResolve', type)` (debugConfigurationManager.ts:148-152). js-debug is registered with `onDebugResolve:node`, so it is never activated.
3. **`pty-host-service.on-pty-host-exit`** restarts the host, but it neither clears `pty-service.ptys` nor tells the renderer. In the code every pty dies with the host, and terminals relaunch or report exit -1 (terminalProcessManager.ts:589-615, baseTerminalBackend.ts:47-60).
4. **`debug-service.on-did-end-adapter`** omits the "Debug adapter process has terminated unexpectedly" error notification (debugService.ts:751-754). Its citation starts at 754, just past that line.
5. **`raw-debug-session.shutdown`** says the disconnect has a 2 s timeout. On the error path the code uses 200 ms (rawDebugSession.ts:604). The model has no error input at all.
6. **`ext-host-search.provide-text-search-results`** says it runs ripgrep in the node extension host. It is a stub with no behavior and no owner definition, so its results are schema fake data. That data includes duplicate resources, which `search-view.file_count` counts as separate files.
7. **`debug-adapter.handle-request`** fixes js-debug's capabilities as constants with no `exceptionBreakpointFilters`, so `setExceptionBreakpoints` is never sent. Real js-debug declares those filters. js-debug lives outside this repo, so this is a modeling assumption to record, not a refuted claim.
8. **World:** `terminal-debug-tasks-seed` seeds `configuration-manager.launch_configurations` without `selected`. The code selects the first configuration at startup (debugConfigurationManager.ts:477-481), so F5 in `full-window` follows the guess path.

Citation spot-check: `--cite-sample 12 --seed 7331` shows all 12 random citations matching their claims (remote agent connection, walkthroughs, emmet, git throttle, notebook execution, ...). 15552 of 15552 citations resolve. I also checked 16 citations by hand in the flows these cases touch: pty-host-service on-exit/start, pty-service create/start/detach/attach, terminal-process.start, local-pty.start, terminal-service before/will-shutdown, debug-service send-all-breakpoints/on-did-end-adapter, raw-debug-session send/shutdown, ext-host-debug-service start/send, search-service split-sync-async, search-actions cancel and search-model.clear. The lines resolve in every case. The wrong claims above are behaviors that don't match their cited lines.

Entry coverage: `search.action.cancel` is covered by an entity that cites the right registration but models the wrong behavior (claim 1). `workbench.action.terminal.new` is not in the inventory; the `terminal-create` flow enters at `terminal-service.create-terminal`. The adapter-exit path has no entry at all (D2).

## 4. Simulator gaps

| Gap | Case | Missing feature |
|---|---|---|
| A step starts only after every timer of the previous step has fired | T2 | A step option to start once the previous entry call returns, leaving timers pending (or `at_ms` that may fall before the timers drain). Then a reconnect can land inside a pending grace timer. |
| A running call can't be cancelled from outside | S2 | Overlapping steps, or a cancellation primitive that aborts an outstanding call chain (a CancellationToken that crosses `call`/RPC). Today the only option is an input flag checked before the work. |
| Periodic timers must be finite (`every_ms` + `count`) | T1, T3 (side effect) | An unbounded periodic timer that stops at the end of the run, so heartbeats don't turn into a spurious "unresponsive" after the last beat. |

Streaming (T1 data, S1 progress, T2 replay) is **not** a simulator gap. It can be modeled with
`emit`/`publish` per chunk, and the model doesn't do it.
