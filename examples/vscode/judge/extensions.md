## 2. Wrong claims in the model

1. **`extension-service.initialize`**, step titled "Resolve local extensions, keep the enabled ones…" (cites abstractExtensionService.ts:518-582). It takes a registry snapshot and filters nothing. The code drops disabled extensions, including those disabled by the trust requirement, through `checkEnabledAndProposedAPI` (:525-533). This is why X8 fails.
2. **`workspace-trust-ux-handler`** summary: "Startup trust prompt, restricted-mode banner and status bar entry". No interface shows the banner or the status entry (`updateWorkbenchIndicators`, workspace.contribution.ts:432-443). `banner-part` is a component with no interfaces.
3. **`extensions-auto-profiler`** summary: "Profiles an unresponsive extension host…". It only has a constructor step. The `onDidChangeResponsiveChange` listener, the 5 s profile, the blame and the SILENT prompt (extensionsAutoProfiler.ts:68, 77-245) aren't modeled.
4. **`file-commands.cmd-workbench-action-files-save`**, titled "Save the active editor through the editor service". It reads `input.resource` and never resolves the active editor. The code's `saveSelectedEditors` uses the active editor when the args are empty (fileCommands.ts:505-508). It also can't be called by the command service's request shape (see X7 and the E1 judge).
5. **`extension-service.on-did-activate-extension-error`** stores `state.activation_errors[ext]`. The code's `_onDidActivateExtensionError` only sends telemetry (abstractExtensionService.ts:1289-1304), and `ExtensionStatus` keeps no activation error (only `runtimeErrors`, via `_onExtensionRuntimeError`). This is minor.
6. **`main-thread-commands.execute-command`**: the `registered` choice default is `'known' : 'known'`, so it is always known. The `!CommandsRegistry.getCommand(id)` check (mainThreadCommands.ts:87) is never computed. The notes acknowledge this. It isn't exercised by X7, which has no args.
7. **`ext-host-extension-service.handle-eager-extensions`** models only `*`. `workspaceContains` and remote-resolver eager activation, which are part of the same `Promise.all` (extHostExtensionService.ts:676-680), are absent. This is minor for the benchmark world.
8. **Language service**: `workbench-language-service` has no interfaces, so `onLanguage:<id>` and the bare `onLanguage` (languageService.ts:287-291) are never fired by anything in the model (X1).

## 3. Builder findings (exthost notes §7)

- "Crashes restart forever is wrong": **confirmed**. The host auto-restarts only while fewer than 3 crashes are recorded within 5 minutes; after that comes the Bisect / Restart / Learn More prompt. Exit code 55 never auto-restarts (nativeExtensionService.ts:164-228; abstractExtensionService.ts:1549-1572).
- "Restart Extension Host after a veto plus Restart Anyway returns `stopped=true` without stopping; `startExtensionHosts` does the stop": **confirmed** (abstractExtensionService.ts:813-815 returns `true` on `confirmed` without `_doStopExtensionHosts`; nativeExtensionService.ts:764-767; `startExtensionHosts` stops first at :960-961).
- "Unresponsive is a missing acknowledgement for more than 3 s, checked every 1 s": **confirmed**. The ack is sent on receipt, before the method runs (rpcProtocol.ts:119, 158, 182-218, 377-379).

## 4. Simulator gaps

1. **Emits from a late callee are delivered at the caller's time, not at the time they were emitted** (X5). `ext-host-rpc-protocol.receive-request` emits the ack at 6002 ms, after the latency fault. The caller timed out at 4001 ms, and the ack is delivered at 4003 ms, so "responsive again" happens about 2 s too early. A trace assertion on recovery time would be wrong. Missing feature: deliver a late branch's `emit` at its own virtual time, or after the entry while keeping its timestamp.
2. **Polling timers** (X5, acknowledged by the builder). The 1 s `RunOnceScheduler` that re-arms until `now > unresponsiveTime` is approximated by a fixed call `timeout_ms` of 3000 + 1000. Missing feature: a `every_ms` timer whose `count` is bounded by a condition, or "wait until a state predicate holds".
3. **Shared pending promises** (X1, acknowledged by the builder). `ExtensionHostManager` caches the activation *promise*, so a concurrent second caller would wait on it. The model answers `cached: true` immediately. Sequential steps don't expose this, but concurrent ones would.
