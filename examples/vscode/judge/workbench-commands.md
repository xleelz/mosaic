# Judge: workbench-commands (C1–C7)

I judged the merged model `examples/vscode/vscode.json` against microsoft/vscode 1.144.0 in
`/home/lbethay/.cache/mosaic-bench/vscode-1.144.0`, with the `full-*` worlds from `worlds.yaml`.
The scenarios are in `judge/scenarios/C1.yaml` to `C7.yaml`, with no mocks. To run them:

```sh
go run ./internal/devtools/check -q -f examples/vscode/vscode.json -f examples/vscode/judge/scenarios/C<N>.yaml --scenario '^bench' --trace
```

## 2. Wrong claims in the model

1. **`keybinding-service.dispatch` runs workbench-shell commands directly** (`call: = state.handlers[...]`). It cites `commandService.ts:80-105`, but `_doDispatch` always calls `this._commandService.executeCommand(...)` and doesn't await it (`src/vs/platform/keybinding/common/abstractKeybindingService.ts:386-390`). As a result, a keybinding never fires `onCommand:` activation for those commands.
2. **`keybinding-service.dispatch` takes the context from the request.** The code reads `contextKeyService.getContext(target)` (`abstractKeybindingService.ts:334`), so the `context-key-service` state never influences resolution. Its `when` evaluator supports only `k` and `!k`, and the seed renames closeGroup's `ContextKeyExpr.and(ActiveEditorGroupEmptyContext, MultipleEditorGroupsContext)` (`editorCommands.ts:866`) to `activeEditorGroupEmptyAndMultipleGroups`, a key that doesn't exist.
3. **`configuration-service.get-value` accepts `override_identifier` and `resource` but ignores both.** Its summary ("policy, else workspace, then user, else default") leaves out the folder, memory and application layers and the language override, which is applied after consolidation (`configurationModels.ts:1033-1085`). It also cites the platform `ConfigurationService`, while the workbench's `IConfigurationService` is `WorkspaceService` (`src/vs/workbench/services/configuration/browser/configurationService.ts`). The two use the same `Configuration` class.
4. **The editor open path never resolves the text file model** (`editor-service.open-editor`, then `editor-group-view.open-editor`). In the code, `EditorPanes` and `TextFileEditor.setInput` resolve `TextFileEditorInput`, which goes through `TextFileEditorModelManager.resolve`. In the model, `text-file-models.resolve` is reached only from save-as, revert, file events and bulk edits.
5. **`command-service.execute-command` leaves out two branches.** One is the `activationEventIsDone` short-circuit (`commandService.ts:61-63`). The other is the race of `*` activation against `CommandsRegistry.onDidRegisterCommand` for the id (`:82-86`): in the code, a command that registers during `*` activation runs. In the model, an unregistered command always waits for `*`, then fails if it isn't in the seeded registry.
6. **`editor-group-view.handle-close-confirmation` is missing a branch.** Auto save `onWindowChange` saves instead of prompting on native Windows and Linux (`editorGroupView.ts:1794-1798`), but the model handles only `onFocusChange`. It also leaves out the `shouldConfirmClose` re-check after the dialog (`:1843-1845`). It doesn't change C5 under the default `files.autoSave=off`.
7. **`native-working-copy-backup-tracker` has no `restoreBackups`.** Its constructor sets `unrestored` but never opens editors for the backups (`common/workingCopyBackupTracker.ts:63`, `356+`).

All the other citations I read beside the code for these flows say what the code does: `commandService.ts:52-105`, `commands.ts:129-135`, `keybindingResolver.ts:320-392`, `editorCommands.ts:835-876`, `commandsQuickAccess.ts:291-293`, `lifecycleService.ts:36-61`, `lifecycleMainService.ts:517-616`, `workingCopyBackupTracker.ts:50-209`, `editorGroupView.ts:1558-1581` and `1738-1883`, `editorGroupModel.ts:290-420`, `editorGroupFinder.ts:167-189`, `textFileEditorModel.ts:328-334`, `configurationModels.ts:1033-1070` and `files.contribution.ts:128`. A random `--cite-sample 10 --seed 77` also resolved 10 of 10. One of those (`automation-service.create-automation`) cites the interface declaration rather than the implementation.

Covered entry points: C1, C4, C5 and C6 run through entities that model the behavior. C2 does too, but with the path defects above. C3's entry (`workbench.action.showCommands`) is modeled only as far as `quickAccess.show`. C7's entry is modeled at the group level only.

## 4. Simulator gaps

- **Restarting a window inside one scenario (C4).** Mosaic can't dispose a renderer instance's in-memory state while keeping its on-disk state (the backups) and then start it again. So close, then restart, then restore has to be split into two scenarios, with the backup carried over by hand as seeded state.
- **Scenario `state` merges into fixture state instead of replacing it (C4, a world note).** `files-search-scm-seed` seeds unqualified `text-file-models.models` with `main.ts`, and setting `text-file-models@w1: {models: {}}` doesn't remove it. The C4 restore case therefore uses `util.ts`. This is a world-layering issue rather than a missing feature, but it stops a scenario from starting from "no model yet" for a seeded file.
- **Data-driven `when` expressions (C2), minor.** Mosaic can't evaluate a CEL string held in state (no `eval`), so context-key expressions stored as data (keybindings, menus) have to be hand-interpreted in CEL. That's why the builders cut `when` down to one key. A restricted evaluator over `&&`, `||`, `!` and `==` would let the model keep the real expressions.
