## 2. Wrong claims found in the model

1. **`range-streamer.fetch-async` picks the wrong stream source.** The model takes the first natural replica of each range other than self (`ring-iterator` at `r.right`, rf 1, excluding self). Under `cassandra.consistent.rangemovement` (default true) the code takes the old endpoint minus the new endpoints: the replica that **loses** the range (`RangeStreamer.java:494-521`). Bootstrap fails if a source filter removes that replica (`:519-521`). The model's `description` admits the shortcut, but the step cites `:237`/`:314` as if the code did it this way. It is visible in `bench-g3-strict-sources`: all three sources differ from the code.
2. **`gossiper.start` does almost none of what it claims.** Its summary and its citations (`Gossiper.java:2014-2032, 2126-2137, 2198-2204`) say it builds the seed list without self, initializes local state and schedules the GossipTask every second. Its behavior:
   - uses a store `update` instead of putIfAbsent, so on a fresh node it fails silently and the next `add-local-application-state` aborts (`bench-g3-fresh-node-local-state`). On a node that already has state it also overwrites the heartbeat with 0, which putIfAbsent wouldn't do;
   - schedules no timer (`bench-g1-scheduled-every-second`);
   - builds no seed list.
3. **The fixture puts the node itself in its gossiper seeds.** `three-node-rf3`/`four-node-rf3` set `gossiper@n1.seeds: [n1]`. `Gossiper.buildSeedsList` skips the local address (`Gossiper.java:2126-2134`), so n1's `seeds` should be empty. This has no effect on the paths tested, because `maybe-gossip-to-seed` returns early when the only seed is self, and in the code an empty list returns early too. A probability using `size(seeds)` on n1 would still be off by one. (`fixtures.yaml` is the coordinator's.)
4. **`storage-service.unbootstrap`'s branch for `transfer_hints_on_decommission: false`** is titled "Pause dispatch and delete hints" but only calls `hints-service.pause-dispatch`. The code also disables hinted handoff and calls `deleteAllHints` (`StorageService.java:5476-5481`). This is not on the deployed config's path.
5. **`boot-strapper.get-bootstrap-tokens`.** The summary says it uses `initial_token`, else allocation for `allocate_tokens_for_local_replication_factor`. The behavior returns the first ring token minus a constant. It is a deterministic stand-in that the summary doesn't disclose. It is harmless for the cases, but the claim is wrong.
6. **Membership models only one endpoint-state subscriber.** Only `storage-service.on-dead`/`on-alive` subscribe. In the code, `LoadBroadcaster`, `DiskUsageBroadcaster`, `DefaultSchemaUpdateHandler` and `ActiveRepairService` also register with the Gossiper (`Gossiper.instance.register`), and `ActiveRepairService`/`RepairSession` register as FD listeners (`ActiveRepairService.java:499, 837`). So conviction doesn't fail running repair sessions in the model. This is an incompleteness that G2's expectation doesn't require.

**Citation spot-check.** `--cite-sample 12 --seed 22`: all 12 claims match the cited code. I also read these behaviors next to their code:

## 4. Simulator gaps

Round 1's gaps that DESIGN §11 resolved:
- **Chaining entries (H1, G3, G4)**: multi-step scenarios (§11.7).
- **Per-node state and two-sided gossip (G1)**: instances and `on:` (§11.1).
- **Asserting call inputs (G3, G4)**: `trace` in expectations (§11.8).
- **Randomness (G1)**: `random(n)` (§11.8).
- **Parallel futures and timeouts (G4, H3)**: `parallel`/`branches` with joins and timeouts (§11.2).
- **One clock (H2)**: epoch plus virtual time (§11.3), which is what made W1 fixable.

Still open:
- **No overlap with a running step (G3, G4).** A step's `at_ms` earlier than the previous step's end is clamped **silently**: G4's peer step at `at_ms: 1000` ran at 60,485 ms, with no warning. Timers are also delivered only after the current top-level call tree. Together these mean nothing can happen on another instance while one instance sits in a long `wait`: peers can't learn BOOT or LEAVING during RING_DELAY, and a write can't race the stream. My G3 and G4 scenarios therefore drive the peer side after the joining or leaving node finishes. Each instance's behavior is right, but the interleaving is not shown. Two things would fix it: concurrent top-level activities (steps that overlap in virtual time, or timers that fire during a `wait`), and a warning when `at_ms` is in the past.
- **A fixture can't remove a node or a key (G3).** A "fresh node joins" world can't be built from `four-node-rf3`, because maps merge and keys can't be deleted. I had to override the topology on `three-node-rf3` and hand-seed n4's gossiper, FD, token metadata and storage-service state. A per-scenario `unset`, or fixture parameters, would help.
- **Shared state between concurrent branches doesn't interleave (G4).** Branches run in list order (§11.2). This matters little here, since the stream and the hints transfer touch different state.

Not a simulator gap: G1's missing 1 s schedule. Timers can express it (`hints-service.start-dispatch` already uses one). It is a model omission.
