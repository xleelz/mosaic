# Judge report: hints-membership (H1–H3, G1–G4)

Model: `examples/cassandra/cassandra.json` (merged). Code: cassandra-5.0.9. `src/` means `src/java/org/apache/cassandra/`.
Scenarios: `judge/scenarios/{H1,H2,H3,G1,G2,G3,G4}.yaml`, 30 scenarios in all. 27 pass. The 3 that fail are deliberate: they assert what the code does where the model is wrong (H2 ×2, H3 ×1). I read the call trees for every scenario, using an in-memory tracer over `internal/sim` and then `check --trace`.

## 2. Wrong claims in the model

- **W1 `storage-proxy.should-hint` (persistent window), units mismatch.** It computes `state.epoch_ms_at_start + now - state.max_hint_window_ms > vars.oldest.value.timestamp`, but hint `creation_time` is on the sim clock (`storage-proxy-hint-runnable.run` sets `creation_time: = now`). As soon as one hint for a host reaches hints-store (after the 10 s flush), every later hint for it is refused as "hint window expired". In the code both sides are epoch ms (`StorageProxy.java:2475-2476`). This is the most consequential error in my group: hints stop after the first flush.
- **W2 `gossiper.endpoint-state-mark-dead` sets `down_since_ms: = now`.** `EndpointState.markDead` only clears `isAlive` (`src/gms/EndpointState.java:260-263`). The downtime timestamp is written only by `Gossiper.silentlyMarkDead` (`Gossiper.java:1529`). Because `gossiper.mark-alive` calls the former before every echo (`Gossiper.java:1437-1439`), the model restarts a down node's hint-window clock whenever newer gossip about it arrives.
- **W3 `abstract-write-response-handler.get` doesn't wait.** It fails immediately when acks < blockFor and nothing failed. The code awaits the write timeout (`AbstractWriteResponseHandler.java:112-121`). This is visible for CL ANY with every replica down: 45 ms instead of ~2000 ms. (This is coordination's entity.)
- **W4 `range-streamer.fetch-async` streams from `gossiper.get-live-members`, including the local node, with no ranges.** RangeStreamer excludes self (`src/dht/RangeStreamer.java:237-243, 314`) and computes a source per range, strict when `consistent.rangemovement` is on.
- **W5 `storage-service.unbootstrap` hard-codes `peers: = []` on `stream-plan.execute`.** The code streams the ranges from `getChangedReplicasForLeaving` to their new owners (`StorageService.java:5438-5452`).
- Minor:
  - `hints-dispatch-trigger.run` lacks the `!isScheduled(store)` filter (`HintsDispatchTrigger.java:58`).
  - The trigger's first pass runs at t=0; the code's initial delay is 10 s (`HintsService.java:229`).
  - `storage-service.excise` emits `hints-service.excise` immediately; the code delays it by min rpc + write timeout, 4000 ms (`StorageService.java:3526-3528`).
  - `maybe-gossip-to-seed` always picks the first non-self seed; the code draws randomly from all seeds, self included.
  - HintVerbHandler's `applies-locally` and the apply run against 10.0.0.1's identity and state, not the receiver's (cluster-convention limit).
- **Narration.** Membership and hints put `title`/`source` on `if` steps, so the trace prints the note even when the branch is false. Examples are "Gossip disabled", "Handled by a peer (not modelled)", "No seed seen", "Local pause detected", and "This node is always alive to itself" for 10.0.0.2. A reader of the trace sees events that didn't happen. The title belongs inside `then`.

Contract seams:
- **C1** `stream-plan.execute` takes only `{operation, peers}`, so membership can't say which ranges go where.
- **C2** The `gossiper.add-local-application-state` request enum lacks `SCHEMA` and `SEVERITY`. This causes 27 schema-validation warnings in schema-auth and ops scenarios.
- **C3** The known `keyspace` seam affects nothing I score. My H1 hint targets `ks1.orders`, which is logged and skipped as a non-existent table. That doesn't change dispatch or deletion.

Citation sample (`--cite-sample 12 --seed 41`): 11 of 12 claims match the cited code. One is off by one: `snapshot-verb-handler.do-verb` cites `Verb.java:183` (SNAPSHOT_RSP); SNAPSHOT_REQ is at :184. I also read these behaviors next to their code:
- **Accurate:** should-hint (except W1), hints-store.is-live, find-oldest (returns Long.MAX on empty), failure-detector.interpret/is-alive, gossiper-gossip-task and its helpers, mark-dead, decommission's checks and order, handleStateBootstrap/Normal/Left.
- **Wrong:** W2, W4, W5.

## 4. Simulator gaps

- **Chaining entries with different interfaces (H1, G3, G4).** A run has one entry interface. "Node comes back, then the next trigger dispatches" and "BOOT gossip, then a write, then NORMAL" each had to be split into separate scenarios with hand-carried state, or approximated with a call-indexed fault on `failure-detector.is-alive` (H1). A scenario-level sequence of entries sharing state would express these directly.
- **Per-node state and two-sided conversations (G1).** SYN→ACK→ACK2 crosses two nodes. With one gossiper state the peer side is "delivered to peer", so each leg is a separate flow.
- **Asserting call inputs (G3, G4).** Expectations see `calls` counts but not call inputs. W4 and W5 (`peers` on `stream-plan.execute`) show only in the trace and can't be asserted without an ontology edit that copies them to `ctx`. Something like `inputs['iface'][i]` would make them testable.
- **Randomness (G1).** The gossip target and the unreachable/seed draws are rotations and choices, with no seeded random in CEL.
- **Parallel futures (G4, H3).** Batchlog replay and the stream run concurrently in unbootstrap, but `foreach` and `call` are sequential. "Wait until signalled or timeout" (H3's get()) has no primitive; the model must add an explicit `wait` itself.
