# mosaic web

The browser UI for mosaic. Use it to browse models, which the docs and CLI call ontologies
(components, interfaces, behaviors, flows, scenarios), to see how far to trust each one, and to run
and play back simulations of requests flowing through a system. The HTTP
contract it relies on is [docs/DESIGN.md](../docs/DESIGN.md) §6.

Stack: Next.js 16.4 (App Router, Turbopack, Cache Components), React 19.3, TypeScript 5.9 (strict),
Tailwind CSS 4.3, `@xyflow/react` 12 and `elkjs` 0.12 for the architecture map, and hand-written SVG
for the sequence diagram. There are no other runtime dependencies.

## Two data sources

The UI talks to one typed client (`src/lib/api/client.ts`, `MosaicClient`). There are two
implementations behind it.

| Mode | Enabled by | Client | Reads |
|---|---|---|---|
| **Server** (default) | nothing | `HttpClient` (`src/lib/api/http.ts`) | `/api/mosaic/v1/...`, which a server-side route (`src/app/api/mosaic/[...path]/route.ts`) proxies to `${MOSAIC_SERVER}/v1/...` |
| **Fixtures** | `NEXT_PUBLIC_MOSAIC_FIXTURES=1` | `FixtureClient` (`src/lib/api/fixtures.ts`) | `web/fixtures/**` through the `/fixture-data/...` route |

`src/lib/api/types.ts` mirrors the Go wire types field for field. Its sources are `pkg/api/types.go`,
`internal/model/{model,analysis,validate}.go` and `internal/sim/sim.go`. The clients turn Go's
`null` lists into empty arrays at the boundary and never rename a field.

### Server mode

```sh
# 1. Start mosaicd (default address 127.0.0.1:7878), then load an ontology, e.g.:
mosaic ontology create envoy-demo --name "Envoy proxy"
mosaic apply envoy-demo -f examples/envoy/ontology.yaml -m "Initial model"

# 2. Run the UI.
cd web
pnpm install
pnpm dev                                         # http://localhost:3000
MOSAIC_SERVER=http://127.0.0.1:7979 pnpm dev     # if mosaicd listens somewhere else
```

The browser only ever calls `/api/mosaic/...`. A route handler proxies these calls, so mosaicd
needs no CORS setup. It forwards the method, headers, query and body, streams the response back, and
passes status codes and error bodies through unchanged. If mosaicd can't be reached, it answers 502
with an `unreachable` error.

- `MOSAIC_SERVER` (default `http://127.0.0.1:7878`) and `MOSAIC_TOKEN` are **server-only** variables,
  read on every request. Neither is fixed at build time, so one build can point at any mosaicd. Set
  them for `pnpm dev` or `pnpm start`:

  ```sh
  pnpm build
  MOSAIC_SERVER=http://127.0.0.1:7990 MOSAIC_TOKEN=... pnpm start
  ```

- If mosaicd runs with `--token`, set `MOSAIC_TOKEN` to the same value. The proxy adds
  `Authorization: Bearer ...` itself and drops any `Authorization` or `Cookie` header the browser
  sends, so the token never reaches the browser or the client bundle. (`NEXT_PUBLIC_MOSAIC_TOKEN` is
  gone.) Without the right token, pages show "a valid bearer token is required ... set MOSAIC_TOKEN"
  and the badge shows `✗ mosaicd unauthorized`.
- The header badge shows `● mosaicd <version>` when `GET /v1/health` answers and
  `✗ mosaicd unreachable` when it doesn't.
- Next to it, a chip shows the running commit (`GET /v1/system/version`), and "N new commits" when
  mosaicd's checkout is behind its upstream. Its popover checks now and runs **Update and restart**
  (`POST /v1/system/update`), which needs mosaicd under `scripts/serve.sh` to restart on its own
  (docs/DESIGN.md §8). In fixture mode it reports "not available: fixtures mode".

### Fixture mode

```sh
cd web
pnpm install
NEXT_PUBLIC_MOSAIC_FIXTURES=1 pnpm dev
# or as a production build:
NEXT_PUBLIC_MOSAIC_FIXTURES=1 pnpm build && NEXT_PUBLIC_MOSAIC_FIXTURES=1 pnpm start
```

`NEXT_PUBLIC_*` values are inlined at build time, so set the variable for `build`. The fixture route
also checks it at runtime, so set it for `start` too. A **◇ fixtures** badge is shown in the header.

The fixtures were generated by the real engine from `examples/language-demo/ontology.yaml` and
`examples/envoy/ontology.yaml` (the generator's defaults).
Fixture mode works like this:

- Every read works: list, detail, document, graph, revisions, validation and the plan for each flow.
- **Running a scenario without overrides** returns its recorded run (`runs/<scenario>.json`).
- **Ad hoc runs** (a flow with no scenario) and **runs with overrides** (choices, faults, state,
  input, seed or extra expectations) show a clear "Not available in fixture mode" notice. They need a
  live mosaicd.
- `POST /test` returns `test-report.json`. Every result links to its recorded run.
- The diff is always empty for a generated ontology, because it holds a single revision with a clean draft.

More fixture ontologies are listed when their directories exist (`EXTRA_ONTOLOGIES` in
`src/lib/api/fixtures.ts`), among them:

- **`commits-demo`** (hand-written, `web/fixtures/commits-demo/`). A small shop model across four
  commits and four revisions: `1a2b3c4` creates it, `2b3c4d5` changes only docs (r2 is identical to
  r1), `3c4d5e6` adds a component (`fraud`), removes one (`legacy-cache`) and modifies one
  (`orders`), which affects the `checkout` and `order-lookup` flows, and `4d5e6f7` creates the
  `refund` flow and modifies `checkout`. A numeric `?rev=N` reads `document.rN.json`,
  `graph.rN.json` and `plan.<flow>.rN.json`, falling back to the unsuffixed (latest) files.
  `commits.json` is an `api.CommitList`. The fixture client computes `/diff`, `/impact` and
  `/commits/{sha}` from the revision documents and plans (`src/lib/model/impact.ts`), so these
  match what mosaicd does in shape but are only an approximation of its rules.
  The source documents are in `commits-demo/source/r1.yaml` to `r4.yaml`. To rebuild, run
  `go run ./internal/devtools/fixtures -in web/fixtures/commits-demo/source/rN.yaml -out /tmp/cdgenN`
  for each revision, then copy `document`, `graph` and `plan.*` with the `.rN` suffix (r4's also
  unsuffixed). `commits.json`, `revisions.json` and `detail.json` are hand-written.

To regenerate the fixtures (from the repository root):

```sh
PATH=/usr/local/go/bin:$PATH go run ./internal/devtools/fixtures -out web/fixtures
```

## Pages

The workspace's tabs are `Overview  Map  Flows  Runs  |  Evidence  History`, and every older route
still works ([docs/ux-plan-2026-11.md](../docs/ux-plan-2026-11.md) has the decisions behind this).
Each route belongs to one tab:

| Tab | Routes | What it answers |
|---|---|---|
| Overview | `/o/<id>` | What this is, entry points, main flows, how far to trust it, where to go next |
| Map | `/o/<id>/map`, `/o/<id>/world` | What it's made of. `/o/<id>?c=...`, the old map link, redirects here |
| Flows | `/o/<id>/flows` | What it does: the happy path first, and search across flows and scenarios |
| Runs | `/o/<id>/simulate`, `/o/<id>/runs/<run>` | What happens: the form, recent runs, playback and compare |
| Evidence | `/o/<id>/evidence`, `.../evidence/tests`, `.../evidence/race-search` (old: `/tests`, `/explore`) | How good it is |
| History | `/o/<id>/revisions`, `/o/<id>/commits` | How it changed: a per-area summary first, then the entities |

What's new in each, and what the longer list below leaves out:

- **Trust.** `components/trust/` owns the fidelity marks: modeled (solid), partial (half), shell
  (hollow), absent (dashed). The passport chip reads `GET /v1/ontologies/{id}/evidence?rev=` through
  `useEvidence` (`lib/evidence.ts`), and shows on each model's card and workspace header. No stored
  evidence reads "Not benchmarked". A figure measured on another revision says so. Green is kept for
  checks against something outside the model, so "Schema OK", a run's "ok" and self-checks are
  neutral. A run's durations say "virtual" and its inputs say "generated".
- **Map.** Models of 120 components or more with areas open on the Atlas (`components/map/AtlasMap`,
  `lib/model/atlas*`), which draws at most 40 boxes per view and groups the rest. `?area=`, `?in=`,
  `?role=` and `?rest=` name the view, `?lens=` picks Area, Failure, Flow or Data, `?c=` selects, and
  `?select=` goes to wherever a component is drawn. Absent mechanisms show as dashed ghost rows. Smaller
  models keep the compound map. Esc or ✕ closes the side panel.
- **Runs.** A run opens on a summary trace (`lib/sim/beats.ts`), with `f`, `e` and `n` to jump to the
  first fault, the first error and the next state change, swimlanes by area, and a warning that lists
  the partial and shell mechanisms it passed through. `?compare=<run>` puts any two runs side by side
  (`components/compare/`).
- **Evidence.** The passport in full, with what each figure is and isn't, the gate statuses in plain
  words, per-area strips, and a filterable list of mechanisms. Self-checks keep the last report per
  revision and always carry their caption. Race search says "Not explored yet" when no replay exists.
- **Search.** `/` or Ctrl/Cmd-K searches everything (`components/palette/`), and `?` lists every key.
- **Scale.** `components/WindowedList.tsx` is the one long list: it draws only what's near the
  viewport. Its row logic is in `lib/windowing.ts`, and fixed-height rows use `playback/VirtualRows`.
  The query cache is a bounded LRU (`lib/querycache.ts`), and validate results are kept per revision
  hash (`lib/validationcache.ts`). The proxy gzips JSON (`app/api/mosaic/[...path]/compress.ts`).

The pages in more detail:

- **`/`: Models.** One card per model, with its passport, description, latest revision, revision
  count, draft state and entity counts.
- **`/o/<id>`: Workspace.** The header has a revision selector (latest, draft or rN), the schema
  status and a draft-changed flag. The selected revision is carried in `?rev=` across tabs. Its pages
  are:
  - **Map, on the compound layout.** An ELK compound layout. Components nest by `parent` and are colored by
    `layer` or by `kind`, with a legend. Derived `calls` edges are solid, derived `emits` edges are
    dotted, and explicit links are dashed violet with a label. Edges that leave a container run along
    the gaps between cards instead of across them. You can pan, zoom (+, −) and fit. To open a
    component, click it, focus it and press Enter, or pick it in the **Components** list on the
    left (toggle it with **☰ Components**). The list is a collapsible tree by `parent`, or, when
    components carry `attributes.area` or `attributes.owner`, flat under each area. It has a
    filter (matches show with their ancestors open), member counts, and starts collapsed above 50
    components. Selecting a component opens its ancestors in the list. The side panel shows
    kind, layer, summary, sources (`path:line`), parent and members, relations, attributes, initial
    state, and every interface. For an interface it shows the request and response schema fields (or
    raw JSON), errors, latency, and its behavior as nested blocks: call, if, choice, foreach (with break and continue), set,
    return, fail, emit, wait and notes. A declarative `store` operation (op, table, key, value, where,
    default, not_found, conflict) is shown as its own block. CEL is shown in monospace. Retry policies, `timeout_ms` and
    `on_error` are all visible, and interface references link to their component. `?c=` and `?i=`
    deep-link to a component and an interface.

    Containers can be collapsed with the ▾ / ▸ toggle in their header. A collapsed group is drawn
    as one card ("N inside"), and edges to its members are merged onto it. Maps with more than 120
    components (`COLLAPSE_ABOVE`) open with their top-level groups collapsed, which turns a map of
    several hundred components into a few dozen cards. **Collapse top level** and **Expand all**
    sit bottom left. A selected or focused component always has its groups opened.

    **Before/after mode.** Use `?commit=<sha>` (the revisions on either side of the commit) or
    `?before=N&after=M` (a missing or zero `before` means `base`, the empty model). The union of
    both graphs is laid out once:
    - **Overlay** (default) draws the union graph. Added components have a green border, modified
      ones amber (the component or one of its interfaces changed), and removed ones are red,
      dashed and struck-through ghosts taken from BEFORE. Each one also carries a text chip. Added,
      modified and removed edges use the same colors, with removed edges dashed.
    - **Side by side** draws BEFORE and AFTER from the same layout, with one shared viewport, so
      positions line up while you pan and zoom.
    - By default only changed components, the ends of changed edges, their direct neighbours and
      their ancestors are drawn. **Show everything** draws the whole union. **Changed only** dims
      everything that didn't change.
    - A legend explains the marks. Clicking a component opens a panel with a field diff (a
      before/after JSON line diff) of the component and its changed interfaces, plus its changed
      edges.
  - **Flows.** With 30 flows or fewer (`SMALL_FLOWS`), every flow is shown expanded, one after the
    other. Larger ontologies get a browser instead:
    - a left rail of **sections** with counts. **Group by** feature tag (`feature:*` in
      `flow.tags`), area (`attributes.area`, else `attributes.owner`, of the component the entry
      interface belongs to, else of the caller, inherited from the nearest ancestor that has one),
      or the top-level parent of that component. Flows with no key go to **Other**. The default is
      feature tag when more than half the flows have one, else area when more than half resolve
      to one, else top-level parent. **All flows** lists every flow;
    - the section's flows as collapsed rows (name, id, tags, scenario count). Expanding a row
      renders its detail and only then fetches its plan;
    - a search box that filters by name, id or tag (every word must match) and updates the counts;
    - `?group=`, `?section=` and `?flow=` in the URL, pushed to history, so links and back/forward
      work. A link to `?flow=` (or an older `#flow-<id>`) opens its section with the flow expanded.

    Plans are fetched through a queue, four at a time (`planQueue` in `src/lib/hooks.ts`). Lists
    over a page long (flow rows, scenarios, test results, configs, component rows) render a page at
    a time and grow as you scroll (`ProgressiveList` in `src/components/ui.tsx`).

    A flow's detail is its entry and narrative, then its plan: reachable interfaces grouped by
    component, choice points with their defaults, faultable targets, stateful components and their
    initial state, any dynamic call sites, and any `unknown` targets that are not interfaces. A
    repeating entry shows its count and interval. Then the flow's scenarios, each with its mechanisms,
    overrides and expectations, plus **Configure** and **Run** buttons.

    With `?commit=<sha>`, the tab lists the flows that commit **created**, **modified**, removed
    (shown only when there are any) and **affected**. Affected flows are listed with their reasons
    (`kind:id`), and each reason links to that component on the before/after map. Expand a flow to
    see a line diff of its definition (or the unchanged definition) and how its reach changed (the
    interfaces it reaches that were added or dropped, from the plans at both revisions). **← All
    flows** goes back to the normal list.
  - **Runs: the form (`/simulate`).** Pick a flow and optionally a scenario. The controls come from the plan:
    - one select per choice point, with the default marked ★ and the scenario's own choice noted;
    - fault rows: a target from `plan.faultable`, a type (`unavailable`, `error`, `latency` or
      `timeout`), and `code`, `status`, `latency_ms` and `calls`;
    - a JSON editor for each stateful component, prefilled with its initial state merged with the
      scenario's;
    - an entry-input editor and a seed;
    - optional extra CEL expectations.

    Only real overrides are sent. The request overlays the scenario: faults and expectations are
    appended, and state and input are deep-merged. After a run, playback is shown inline. **Recent
    runs** lists the saved runs.
  - **Commits.** The code commits imported for the ontology (docs/DESIGN.md §10), newest first.
    Each row shows the short sha (linked to `commit.url` when set), subject, author, date, file
    count, a badge for whether the model changed at that commit, and the revision that models it.
    You can search by sha, subject, author or file, and filter to **only commits that change the
    model**. `?sha=` selects a commit (any unique prefix of 7 or more characters). The detail shows
    the header (sha linked to `commit.url`, or else to the revision's `source.url`), the revisions
    before and after, an impact table (added, modified and removed counts by kind, plus the
    affected flows), the changed files, and links to **View architecture before/after**, **View
    flows changed** and the entity diff in Revisions.
  - **Revisions.** The revision list (browse any of them) and a diff viewer between two revisions
    or the draft. Changes are grouped by kind and shown as line diffs with context. Each revision
    shows the commit it models (`source`), linked to the Commits tab and to `source.url`.
    `?from=&to=` preselects the diff.
  - **Evidence: self-checks.** **Run all** sends `POST /test` with `save=false`, unless you tick
    "Keep traces". The report is stored per revision, so it survives a reload. You get a table with
    search, grouping and "Failed only", per-assertion details and a link to each run.
- **`/o/<id>/runs/<run>`: Playback.** `?at=<seq>` opens at a given event. The page fills the
  viewport with no page scroll. The app bar, the workspace header and tabs, and the run's title and
  meta lines are hidden; they reveal together as an overlay while you hover the top edge (or the
  handle at its centre, which also pins them open until Esc), or focus anything inside them. Below
  the summary and the scrubber the sequence diagram fills the stage. The inspector and state ledger
  float in a right panel and the map along the bottom, each **hidden** (a tab or a slim bar),
  **open** (docked: about 420px wide, or 30% of the height) or **expanded** (60% of the width, or
  75% of the height, over the diagram). Both states are remembered in localStorage. The inline
  playback in the Runs form and Race search keeps the grid layout (`Playback`'s `layout="embedded"`).
  The page has:
  - a **summary** card: status, result or error, duration, calls (with a per-interface table),
    retries, faults, assertions ✓/✗ (with details), warnings and, for a repeated flow entry, a
    per-pass table (start, duration, result);
  - a **timeline scrubber**: reset, step back and forward, play/pause, jump to end, speed 0.5× to 8×,
    and ticks for errors, faults, retries and timeouts;
  - a **sequence diagram** (SVG): lifelines with sticky heads, activation bars, requests
    (`call.start`) and responses or errors (`call.end`) with payload chips, retries (↻ and the attempt
    number), faults (⚡), timeouts (⏱, with a bracket back to the call), late responses (dashed
    amber), async emits and deliveries (dotted), notes as folded annotations, and choices and `set`s
    as markers. The cursor row is highlighted and future events are dimmed. Click a row to jump to
    it;
  - the **architecture map**, highlighting the active component and the components with an open
    call. An animated dot travels the active edge, reversed for responses and colored for errors and
    timeouts;
  - an **inspector** for the current event: input, output or error JSON, a note's title and detail
    with `path:line`, a choice's key, option and origin, a set's path with old → new, retry and
    timeout details, and links between a request and its response;
  - a **state ledger**: `ctx`, the current frame's `vars` and each component's state as of the
    cursor. These are replayed from `summary.initial_state` by applying `set` events. Fields changed
    at the current event are highlighted, and state that differs from the start is marked with a dot.

### Keyboard

| Key | Action |
|---|---|
| Space | Play or pause playback |
| ← / → | Step one event (Shift: 10) |
| Home / End | Jump to the first or last event |
| f / e / n | Run page: jump to the first fault, the first error, the next state change |
| s | Run page: cycle the view (summary, side by side, sequence) |
| i | Run page: cycle the inspector panel (open, expanded, hidden) |
| m | Run page: cycle the map (open, expanded, hidden) |
| / | Search everything |
| Ctrl/Cmd-K | Search everything, even while typing |
| ? | Every key, in a sheet |
| Esc | Close a dialog, the code viewer or the map's side panel |
| Tab, Enter, Space | Move between and activate every control; Enter on a focused map node opens it |

Playback shortcuts are ignored while you type in an input, select or text area, and while focus is
in the code viewer.

### Code viewer

Every code citation (`path:line` under components, interfaces, flows, steps, notes and the run
inspector) is a button inside a workspace. Clicking it opens a floating **code viewer** with the
file at the model's commit: mosaicd fetches it from GitHub (`GET /v1/ontologies/{id}/source`,
docs/DESIGN.md §6) with its own `GITHUB_TOKEN` or `gh auth token`, so private repos work and no
token reaches the browser. Outside a workspace a citation stays plain text. In fixture mode the
viewer says source files are not available.

- The window opens centered at 70% × 70% of the viewport. Drag it by its title bar, resize it from
  its bottom-right corner, and expand it to 95% with □ (or a double-click on the title bar).
  Clicking another citation while it is open reuses the window and swaps the file.
- The title bar shows `repo@shortsha path:L-L`, the **vim** toggle, **Open on GitHub** (the blob
  URL with `#L10-L20`), **Copy path** (`path:L-L`) and ✕.
- The editor is CodeMirror 6, read-only, with line numbers and syntax coloring by extension: Go,
  Python, C/C++ and CUDA (`.cu`, `.cuh`), JavaScript, TypeScript, JSX/TSX, Rust, Java, YAML, JSON,
  Markdown, SQL, shell, HCL/Terraform, protobuf, TOML and Dockerfiles; anything else is plain text.
  The cited lines are highlighted and centered, with the cursor on the first.
- CodeMirror and the languages load on the first click (dynamic imports), never with a page.

Vim keys are on by default, starting in normal mode; the **vim** toggle turns them off, and the
choice is kept in `localStorage` (`mosaic.codeViewer.vim`). The status line at the bottom shows the
mode, pending keys and `line:col`. Edits are no-ops.

| Key (vim on) | Action |
|---|---|
| h j k l, w b e, 0 $ | Move by character, word, line edge |
| gg / G, `:42` | First line / last line, line 42 |
| Ctrl-d / Ctrl-u, Ctrl-f / Ctrl-b | Half page / full page down and up |
| `/text`, `?text`, n / N, `*` | Search forward and back, next and previous match |
| % | Matching bracket |
| v, V, y | Visual and line-visual selection, yank |
| `:q`, q, Esc in normal mode | Close the viewer |

Esc belongs to vim: it leaves insert or visual mode and cancels a pending command, and closes the
viewer only from normal mode with nothing pending. With vim off, arrows, Page Up/Down and Ctrl-F
(search) work, and Esc closes. While the viewer has focus it owns the keyboard, so the run page's
Space, arrows, `i` and `m` don't fire.

## Code layout

```
src/lib/api/        types.ts (Go mirror), client.ts (interface, errors), http.ts, fixtures.ts, normalize.ts
src/lib/sim/        playback.ts: spans, lifelines, state replay, event labels and tones
src/lib/model/      formatting, schema resolution, the categorical palette, impact.ts (entity diff and impact)
src/lib/hooks.ts    a small keyed query cache (useQuery), useDocIndex, useValidation, and the plan request queue
src/lib/evidence.ts useEvidence and the mechanism joins; lib/model/atlas* the area map; lib/sim/{beats,lanes,compare,window,wording}.ts the run view
src/lib/model/docindex.ts  lookup maps built once per document (components, interfaces, flows and
                    scenarios by id, scenarios by flow, members by parent, top-level parent, area),
                    flow grouping and the component tree rows; tests in docindex.test.ts
src/components/     ui primitives, JSON/CEL views, WindowedList, diff.tsx (line diffs), behavior StepList, map/, playback/, workspace/,
                    trust/ (passport, fidelity marks), overview/, evidence/, compare/, history/, palette/
src/components/code/  the code viewer: CodeViewer.tsx (provider and window), CodeEditor.tsx (CodeMirror,
                    vim, theme; lazy), languages.ts (per-language chunks), hcl.ts; lib/source.ts for
                    the language, blob URL and title (tests in source.test.ts)
src/components/map/ ArchitectureMap, layout.ts (ELK), graphview.ts (collapse, before/after union, change scope)
src/app/            routes; fixture-data/[...path] serves web/fixtures in fixture mode
```

The layer and kind colors are the dataviz reference palette's dark steps. Hues are assigned in a
fixed order and never cycled. They were validated against the panel surface (`#11181f`): worst
adjacent CVD ΔE 8.4, normal-vision ΔE 19.3, every color ≥ 3:1. Text tokens are ≥ 5.9:1 on panels.

Colors and order don't depend on the data source. mosaicd returns graph nodes sorted by id, while
the fixtures keep document order. `normalizeGraph` puts both into one canonical order: nodes by id,
edges by from, to, kind and id. Colors go to the layer (or kind) names in sorted order, with
`unspecified` last. Members in the component panel are listed by id. So the same ontology renders
identically from either source.

HTTP interfaces show `METHOD path` in their card header. `method` is optional, and a path is shown
on its own when there is no method. The playback inspector adds a `request` line for a call whose
input is an HTTP request envelope with a `method`.

## Checks

```sh
pnpm build      # type-checks (strict) and builds
pnpm typecheck  # tsc --noEmit
pnpm lint
pnpm test       # node --test on src/**/*.test.ts (Node's built-in type stripping, no extra deps)
```

The document is cached once per revision: `latest` is keyed by its number, so the workspace tabs,
run playback and the commit views share one copy. Look things up in a document through
`useDocIndex(doc)` (or `docIndex(doc)` outside components), not with `find` or `filter` over its
arrays.

On a generated ontology of about 600 components and 600 flows (dev server), the Flows tab used
to send a request per flow (one plan each) and keep the main thread busy for over five minutes. It now sends 5
and is interactive in about 1.2 s.

The UI was verified with headless Chromium (Playwright) against the production build in fixture
mode. The check covered the list, the map with a panel, Simulate, playback of
`retry-before-commit` and `stream-breaks-after-commit` at a mid-run cursor and at the end, and the
Tests tab, with zero console errors. Server mode was smoke-tested against a live mosaicd. Those
scripts live outside this directory, under `/tmp/mosaic-ui-check/`.

The commit views were checked the same way (`/tmp/mosaic-commit-check/shots.js`, saved to
`/tmp/mosaic-commit-shots/`): the commits list, a commit detail, the overlay and side-by-side
before/after maps, flows changed with a flow expanded, affected flows, the collapsed and partly
expanded map of a large generated ontology, and the revision list with source commits. There were no console
errors.

The proxy was tested against `mosaicd --token`. Health, graph, a POST validate and a POST simulation
returned 200 or 201, and a missing ontology returned 404 with its error body. A web server without
