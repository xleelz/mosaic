# Generation pipeline: an operator's runbook

This runbook builds a mosaic ontology from any repository, in the eight stages of DESIGN §13
(plus stage 4b, the in-build oracle), and ends every build and fix round with a blind
re-measurement (DESIGN §13.1 item 31). It generalizes the builds of a private gateway platform,
Apache Cassandra 5.0.9 (`examples/cassandra/`) and VS Code 1.144 (`examples/vscode/`). Those builds appear below only as examples. Nothing in
this runbook is specific to them.

> Requires mosaic with DESIGN §11 (in progress): instances, `parallel`/`join`, deadlines, timers,
> capacity, publish/subscribe, config and fixture entities, multi-step scenarios, trace
> assertions, mocks, and the check flags `--behavior-coverage`, `--lint hollow,trivial`,
> `--no-mocks`, `--min-modeled`, `--min-substantive`, `--max-trivial`, `--tests`,
> `--min-test-reach`, `--features`, `--strict-features`, `--lint racy,seam-names`, `--max-racy`,
> `--max-seam-names`, `--contract`, `--max-contract-issues`, `--scenario` and `--trace`
> (DESIGN §12 and the binding clarifications in §13.1). Until they land, the stages still apply,
> but skip the flags the check tool rejects.

The coordinator, one agent or a person, runs the stages. Area agents, oracle agents and judges
are separate agents, briefed from the templates in `.claude/skills/mosaic-generate/templates/`.
Every repo-specific value comes from one file, the **profile**
(`examples/<repo>/profile.yaml`). Start from `examples/_profile-template/profile.yaml`.

## Layout and shell setup

Everything for one repo lives under `examples/<repo>/`:

| Path | Written by | Stage |
|---|---|---|
| `profile.yaml` | coordinator | before 1 |
| `inventory.json`, `inventory-audit.md` | coordinator | 1 |
| `skeleton.yaml` | coordinator | 2 |
| `fixtures.yaml` (fixtures, plus references to shared configs) | coordinator | 3 |
| `worlds.yaml` (the merged `full-*` worlds; generated by `assign_inventory.py --worlds`) | coordinator | 5 |
| `BRIEF.md` | coordinator, from the template | 4 |
| `fragments/<area>.yaml`, `notes/<area>.md` | area agent | 4, 5 |
| `features` in `profile.yaml` (the user-visible feature list, each with an owner) | coordinator | 2 |
| `test-targets.json` (each test file and the code it tests; `test_targets.py`) | coordinator | 2 |
| `skips/<area>.json` | area agent | 4, 5 |
| `skips/<area>.features.json` (features the area doesn't model, with reasons) | area agent | 4, 5 |
| `build-oracle/<area>.json` (the area's in-build test sample) | coordinator (`sample_tests.py --area`) | 4b |
| `RECONCILE.md`, `reconcile/<area>.txt`, `reconcile/merged-check.txt` | coordinator | 5 |
| `<repo>.json` | coordinator (merged ontology) | 5 |
| `oracle/sample.json` (disjoint from `build-oracle/`), `oracle/<area>.yaml`, `oracle/<area>.md` | coordinator; oracle agents | 6 |
| `BENCHMARK.md` | coordinator, before stage 4, kept from builders | 7 |
| `BENCHMARK<n>.md`, `oracle<n>/`, `judge<n>/` (round n's blind measure; never read by builders) | a separate benchmark agent, before round n; fresh oracle agents and judges | end of every round |
| `judge/JUDGE.md`, `judge/<group>.{md,json}`, `judge/scenarios/` | coordinator, judges | 7 |
| `RESULTS.md` | coordinator | 8 |

Set these once per shell, from the repo root of mosaic. The values come from the profile:

```sh
cd /path/to/mosaic
export PATH=/usr/local/go/bin:$PATH GOFLAGS=-mod=readonly
WS=examples/<repo>                 # profile: workspace
CODE=/abs/path/to/checkout          # profile: snapshot.path (read-only)
CHECK="go run ./internal/devtools/check"
SCRIPTS=.claude/skills/mosaic-generate/scripts
# the stage-2 contract files, if any, as check flags (DESIGN §13.1 item 34)
CONTRACTS=""; for f in $WS/contracts/*.yaml; do [ -e "$f" ] && CONTRACTS="$CONTRACTS --contract $f"; done
```

## The check tool

`internal/devtools/check` merges documents, validates them, runs every scenario, and measures
evidence. It needs no server. Configs and fixtures merge by id: each id has one owner, identical
duplicates merge silently, and differing duplicates are a merge error unless the duplicate is
marked `attributes: {boundary: true}` (a reference that defers to the owner). The flags this
runbook uses:

| Flag | What it does |
|---|---|
| `-f FILE` (repeatable) | Merge these documents. Boundary stubs merge by union; the owner's definition wins |
| `-o FILE` | Write the merged document as JSON |
| `-v`, `-q` | List combined stubs and every uncovered entry point; or print only failures and totals |
| `--code DIR` | Resolve citations against the snapshot |
| `--strict-citations` | Exit 1 on missing paths, lines past the end, or packed citations |
| `--cite-sample N --seed S` | Print N random citations next to the cited code, for a support check by reading |
| `--inventory FILE` | Measure entry-point coverage; `--strict-coverage` exits 1 on an entry neither covered nor skipped; `--coverage-md` writes tables |
| `--min-modeled R` | With `--inventory`, print the modeled level per fragment and in total, and exit 1 when a fragment's modeled / (owned entries − skipped) is below R. An entry is **registered** (the covered count) when a reachable entity cites it or is named for it, and **modeled** only when an interface that cites it or is named for it has a behavior or a `store` and some scenario's trace calls it (DESIGN §13.1 item 13). A fragment owns the entries in files its entities cite or under directories they cite. A file that defines no interface with a behavior or a `store` (the skeleton, `fixtures.yaml`) is reported as `exempt` and never fails the gate |
| `--min-substantive R` | With `--inventory`, the same report counts **substantive** entries: modeled by an interface whose behavior isn't trivial (see `--lint trivial`). Entries of a declaration-only kind (`level: registered`) count once registered. Exit 1 when a fragment's substantive / (owned entries − skipped) is below R (DESIGN §13.1 item 15) |
| `--lint trivial` | With `--inventory`, list the flow-reachable interfaces that cite an unskipped entry (or are named for one) and whose behavior is trivial: no `store` and, at any depth, no `call`, `if`, `when`, `choice`, `fail`, `emit` or `publish`, and at most two `set` steps. Prints the trivial share per fragment. `--lint hollow,trivial` runs both lints |
| `--max-trivial R` | Run `--lint trivial`, and exit 1 when a fragment's trivial share is above R |
| `--lint inert,unscheduled,dataflow` | Model-integrity lints (DESIGN §13.1 item 20). Each lists findings and a share per fragment. **inert**: owned interfaces with no behavior or `store` that a flow, a behavior or an inventory entry (with `--inventory`) says run, including boundary stubs whose owner never defined them. **unscheduled**: interfaces citing a `cron`, `listener`, `queue-consumer` or `service-main` entry (or the `scheduled-task`, `background-task`, `busy-loop` or `process-main` equivalents), or with `attributes.schedule`, that no timer, `repeat` flow or startup flow reaches. **dataflow**: `state` paths and store tables (with literal key prefixes) that a behavior reads but no `set`, store write, fixture or initial state writes. Dynamic paths are counted as unknown, not flagged |
| `--max-inert R`, `--max-unscheduled R`, `--max-dataflow R` | Run that lint, and exit 1 when a fragment's share is above R |
| `--lint racy` | Read-then-write on shared state (DESIGN §13.1 item 28): a behavior that reads a store row or `state` path, then writes the same table and key prefix (or path) with a `put` or `update` without `if`/`if_absent`, outside a `transact`, when it can run concurrently (more than one instance, no `capacity` of 1, or another writer of the table). `attributes.single_writer: "<reason, cited>"` exempts. Each finding names the read, the write, the key and the fix (`if`, `if_absent`, `incr`, `transact`) |
| `--max-racy R` | Run `--lint racy`, and exit 1 when a fragment's share of store-writing behaviors that are racy is above R |
| `--lint seam-names` | One field, two spellings (DESIGN §13.1 item 29): a name read at a seam (store rows, call inputs against the callee's request schema, responses, events) that matches a written name only after normalizing case, `_`, `-` and spaces (`limitUSD` against `limitUsd`). Route inputs and `x_*` header aliases are exempt |
| `--max-seam-names N` | Run `--lint seam-names`, and exit 1 above N findings in total |
| `--behavior-coverage` | Union of every scenario's `executed` steps; per interface, the behavior steps no scenario runs, with unexecuted `fail` and `if` branches listed (DESIGN §12) |
| `--lint hollow` | Fail scenarios that record state `set` events no expectation checks (no expectation mentions `state` or `trace`), and flows tagged `writes` with no multi-step scenario that reads the effect back. Warn (advisory, exit code unchanged) about ok runs that record no `set` though they can reach a state-writing interface. State on components of kind or tag `cache`, `limiter` or `metrics`, or tagged `incidental`, is ignored (DESIGN §12, §13.1) |
| `--no-mocks` | Refuse any scenario that uses `mocks` (DESIGN §11.8) |
| `--tests FILE` | Read `test-targets.json` (`[{test, targets, area}]`, from `test_targets.py`) and report **test reach** per area and in total: a test file is reached when an interface that some scenario's trace calls cites one of its target files (or a directory above one). Reach is over the tests with at least one target; the rest are counted apart. `-v` lists the unreached tests (DESIGN §13.1 item 19) |
| `--min-test-reach R` | With `--tests`, exit 1 when an area's reached / resolved tests is below R. Only areas with a fragment in the merge (`fragments/<area>.yaml`) are gated, so an area's own check doesn't fail on the others |
| `--features PROFILE` | Report the profile's `features` as **covered** (a flow tagged `feature:<id>` exists and a scenario runs it), **skipped** (listed in the owner's `skips/<area>.features.json`, next to the profile, with a valid reason) or **missing**. Skip reasons follow the inventory skip rules: not "not modeled", "out of scope", "too large" or "todo", and a "covered by" reason names the entity in `covered_by`. Features of areas not in the merge are reported apart |
| `--strict-features` | With `--features`, exit 1 when a feature is missing |
| `--failures PROFILE` | Report the profile's `failures` (the failure matrix, DESIGN §13.1 item 22) as **covered** (a flow tagged `failure:<id>` that a scenario runs while injecting a fault, a kill, a cancel or restart step, a failing mock or seeded state), **skipped** (in the owner's `skips/<area>.failures.json`, under the feature skip rules) or **missing**. A failure with `sides: [{owner, role}]` (a two-sided failure, item 30) is covered only when every side is: each owner tags a flow `failure:<id>:<role>` run under injection, or skips its side with `{id, role, reason}`; the report lists each side. Failures of areas not in the merge are reported apart |
| `--strict-failures` | With `--failures`, exit 1 when a failure is missing |
| `--openapi FILE` (repeatable) | Contract conformance (DESIGN §13.1 item 21): match each OpenAPI operation to its interface (`attributes.method` and `attributes.path`, else the name `<method>-<path slug>`) and report missing, extra, required-mismatch and mistyped request and response fields, success and error statuses that disagree, `unmodeled` operations and `orphan` route interfaces. A relative path missing from the working directory is resolved against `--code`. `--max-conformance-issues N` exits 1 above N issues |
| `--contract FILE` (repeatable) | Contracts the spec doesn't cover (DESIGN §13.1 item 34), from `contracts/*.yaml`: `contracts: [{id, match, request, response, errors, stream, sources}]`, `match` being `{interface: <id or glob>}`, `{route: {method, path}}` or `{attributes: {...}}`. Request, response and errors are compared as with `--openapi`; a `stream` (`{frames: [{name, schema}], terminator, order}`) is compared with the yields the run scenarios' traces show, reporting `frame-missing`, `frame-extra`, `frame-order` and `terminator`. Frames no scenario yielded are counted as not compared. `--max-contract-issues N` exits 1 above N issues |
| `--scenario REGEX` | Run only matching scenarios |
| `--trace` | Print each run's trace: calls, notes, faults, retries, instances |
| `--strict-stubs` | Make "stubs disagree" (two boundary stubs with different definitions) an error naming both (DESIGN §15.2) |
| `--stage FILE` (repeatable, or comma-separated) | Staging (DESIGN §15.2): run these `-f` fragments' working copies against every other `-f` fragment's **last-good** copy in `--stage-dir`, or its working copy when it has none. Several fragments form a **joint stage**, validated together. A failed run ends with a report: per staged fragment, its own failing items (conflicts, validation errors, failing scenarios); apart from those, the failures in non-staged copies, a **stale peer** being a last-good copy whose working copy differs; and `~ suggest staging <peer> too` for each stale peer whose working copy changes a failing item or an id a failure names, with a `~ try: --stage ...` line. Gate findings (citations, coverage, lints) are not attributed |
| `--accept` | With `--stage`, record every staged fragment as last-good, all at once and only when the run passes. A failed run records nothing |
| `--stage-dir DIR` | The last-good snapshot directory (default `.mosaic/stage`, gitignored). Each copy lives at its fragment's path relative to the working directory |
| `--lint unknown-inputs,exemptions` | **unknown-inputs**: scenario, step and entry input keys the target's request schema doesn't declare, at any depth (route-header aliases and `x_*` excepted). **exemptions**: each `racy_in_code`, `single_writer`, `reachable_by` and `choice_ok` exemption's citation resolves and its cited lines plausibly support it (with `--code`; without it, only that citations exist and CEL compiles) (DESIGN §15.2) |
| `--lint internal-assertions,clock-ids` | **internal-assertions**: per fragment, the share of expectations that name a non-boundary interface or the state of a component that isn't a store; assert on `io`, `result` and `steps.*` instead. **clock-ids**: id-shaped templates that read `now`; mint ids with `id(prefix, key...)` and `seq(name)` (DESIGN §15.1) |
| `--max-exemption-issues N`, `--max-clock-ids N`, `--max-unknown-inputs N` | Run that lint, and exit 1 above N findings in total |
| `--max-internal-assertions R` | Run `--lint internal-assertions`, and exit 1 when a fragment's share is above R |
| `--explore REGEX --schedules N` | Rerun the matching scenarios under up to N schedules (tie orders, `parallel` branch and join order, `--jitter-ms` at_ms jitter); a failing schedule is written to `--replay-dir` (default `.mosaic/replay`) and `--replay FILE` reproduces it (DESIGN §15.5). A scenario that passes every schedule has its stale replay removed (`--keep-replays` keeps it). Any failure exits 1, unless `--max-explore-failures N` allows N, or the profile's gates record exploration without gating it |
| `--profile PROFILE` | The profile the racy and choice-for-computed lints read, and the **gates**: its `gates:` section gives the defaults of `--strict-stubs`, `--max-exemption-issues`, `--max-internal-assertions`, `--max-clock-ids`, `--max-unknown-inputs` and `--max-explore-failures` (a flag on the command line wins). A missing entry takes the template's value (`examples/_profile-template/profile.yaml`, section 12); unset `max_explore_failures` records exploration failures without gating. The check prints `~ ratchet: --<flag> can go down to N` when a measured value is below its gate |

The **full gate**, used at the end of stages 4, 4b, 5 and 6, and by every fix round:

```sh
$CHECK -f $WS/skeleton.yaml -f $WS/fixtures.yaml -f <fragments...> \
  --code $CODE --strict-citations --inventory $WS/inventory.json \
  --min-modeled 0.5 --min-substantive 0.5 --max-trivial 0.35 \
  --tests $WS/test-targets.json --features $WS/profile.yaml --strict-features \
  --behavior-coverage --no-mocks \
  --lint hollow,trivial,racy,seam-names,unknown-inputs,exemptions,internal-assertions,clock-ids $CONTRACTS \
  --profile $WS/profile.yaml --strict-stubs --explore 'race|concurr' --schedules 20 --replay-dir $WS/replay
```

`--profile` supplies the per-repo thresholds (DESIGN §16.1) from the profile's `gates:`:
`max_exemption_issues`, `max_internal_assertions`, `max_clock_ids`, `max_unknown_inputs`,
`max_racy`, `max_seam_names`, `min_test_reach` (with `--tests`), `max_contract_issues` (with
`--contract`), `max_conformance_issues` (with `--openapi`) and `max_explore_failures`. Don't pass
those flags in the gate: a flag on the command line overrides the profile. `--strict-stubs` is on
in every gate (no repo has stubs that disagree). A profile without `gates:`, or a gate missing
from it, takes the template's value, for a new model: 0 exemption issues, 0.5 internal
assertions per fragment, 0 clock ids, 0 unknown inputs, 0 racy, 0 seam names, 0.5 test reach per
area, 0 contract and conformance issues. `--explore` reruns the scenarios whose id names a race
or concurrency (`race|concurr`) under 20 schedules each. Its failures are always printed, with a
replay file under `$WS/replay`, but they fail the gate only when the profile sets
`gates.max_explore_failures`; otherwise they are recorded for the next fix round. A scenario a
fix round makes pass has its replay file removed, so `$WS/replay` holds only current failures.

**The ratchet.** When a profile is written for an existing model, its gates are today's measured
values, rounded toward passing (shares up, reach down, to 3 places), so the model passes as it
stands (the vLLM, VS Code, Cassandra and gateway-platform profiles were measured this way). After that
they only tighten: a maximum goes down, `min_test_reach` goes up.
- every fix round ends by tightening each gate to the value the check measures (for the count
  gates, internal assertions and exemptions, it prints `~ ratchet: --<flag> can go down to N`);
- a threshold is never raised: a change that adds findings fixes them, in the area that added
  them;
- a gate at 0 stays at 0, and `max_explore_failures`, once set, follows the same rule.

The trivial and substantive thresholds come from the baselines in
`examples/cassandra/quality-baseline.md` and `examples/vscode/quality-baseline.md`: every
Cassandra fragment passes them (at most 33% trivial, at least 82% substantive), while four VS Code
fragments don't (up to 50% trivial; 49% substantive at the lowest). A trivial
interface is often fine (a JMX setter that flips one flag); read the listed ones, and give each
that stands for real logic its behavior. The share, not each hit, is the gate.

The racy and seam-names gates are 0 for a new model because each finding is a bug the scenarios can't see: in
a gateway-platform blind round, compare-and-set modeled as read-then-write hid lost updates and double
claims, and `limitUSD` written by one area and read as `limitUsd` by another passed every
other gate (DESIGN §13.1 items 28 and 29). Fix a racy finding with `if`, `if_absent`, `incr` or
`transact`; exempt a real single writer with `attributes.single_writer` and its citation.

The inventory measures entry points, not the system: vLLM's scheduler-kv, the heart of the
engine, had 8 entries, and the oracle's model bugs were mostly whole features nobody modeled. Two
gates weight the model by what the project itself cares about (DESIGN §13.1 item 19). **Test
reach** counts the repo's test files whose code under test some scenario actually calls; a gate
of 0.5 per area fails one vLLM area (models-layers, 43%) and five VS Code areas (platform-core
20%, builtin-extensions 16%) on the models built before it existed (`quality-baseline.md` in
each). It is generous, since a test counts once any of its target files is cited, so read the
unreached list (`-v`) rather than chase the ratio. **Features** come from the profile, so a
feature the inventory can't see (KV offload, a scheduling policy) is modeled or skipped on the
record.

## Stage 1: Inventory

List every entry point, so coverage can be measured instead of hoped for.

**Inputs.** The snapshot (`snapshot.*`), and `inventory.plugins` and `inventory.kinds` from the
profile.

**Outputs.** `inventory.json` (`{root, counts, entries: [{kind, name, file, line, via, detail}]}`)
and `inventory-audit.md`, which records the measured precision and recall.

**Commands.**

```sh
go run ./internal/devtools/inventory --code $CODE --lang <inventory.plugins, comma-separated> \
  --out $WS/inventory.json
jq '.counts' $WS/inventory.json
# precision: a seeded random sample of entries, read one by one
jq -r '.entries[] | "\(.kind)\t\(.file):\(.line)\t\(.name)"' $WS/inventory.json | shuf -n 40 --random-source=<(yes)
```

1. Run the scanner with the profile's plugins (`--include-test-support` only when the profile
   says so). For logic-level scopes (a component refined to `logic`), add the profile's
   `inventory.opt_kinds` as `--kinds go-func,py-func,ts-func` and its `inventory.scope_paths` as
   `--paths a.go,dir/`: one entry per function or method (`Type.Method`), spanning its lines,
   with `exported`; test functions only with `--include-test-funcs`, flagged `test`.
2. **Precision.** Read a sample of `inventory.audit.precision_sample` entries. Mark each a true
   entry point or a false positive. A false-positive class (for example, every MBean getter, or
   every `for {}` loop in a test helper) becomes a group skip rule in the profile, not a silent
   deletion.
3. **Recall.** Build an independent list of known entry points from `inventory.audit.recall_sources`:
   the protocol or route spec, an OpenAPI file, the CLI's help registry, the docs' feature list,
   and the tests' entry calls. Look each one up in the inventory. Each miss is either added by hand
   (`"via": "manual"`, with a reason in the audit) or filed as a scanner gap for mosaic.
4. Record per kind: counts, precision, recall, and the misses.

**Exit criteria.** Precision and recall at or above `inventory.audit.targets`, for every kind
whose count is at least 10. Every false-positive class is a written skip rule. Every manual entry
has a reason.

**Example.** Cassandra: 1,353 entries over 11 kinds, from the `java` plugin; 913 were
`jmx-operation`, and most of them became group skips (getters with no behavior). A gateway platform: about 900
entries from the `go`, `ts` and `python` plugins; the heuristics were about 95% precise and
weakest on crons.

## Stage 2: Skeleton and contracts

Fix everything two areas must agree on **before anyone writes a fragment**. Every contract the
gateway-platform build retrofitted mid-build was cheaper here.

**Inputs.** The profile's `areas`, `overrides`, `naming`, `errors`, `shared_shapes` and
`shared_components`; the inventory.

**Outputs.** `skeleton.yaml`, the contract sections of `BRIEF.md`, the profile's `features`,
`contracts/*.yaml`, and `test-targets.json`.

`skeleton.yaml` contains:
- external actors (clients, operators) and the deployables and modules, with fixed ids and
  `attributes: {owner: <area>}`;
- shared infrastructure components with `owner: shared` (disks, databases, caches, queues);
- **shared schemas** for every shape in `shared_shapes.schemas`, defined once, under their
  owner's name;
- **predeclared seams.** For each cross-area call the coordinator can already see (an interface
  the inventory, the module graph or the profile names as called by another area), a boundary
  stub with the owner's request, response, kind and errors, and
  `attributes: {boundary: true, owner: <area>}`. Area agents copy these; they never guess.
- the instance groups' parent components (`instances.groups[].component`).

**Features.** Write the profile's `features` now, before fan-out: `[{id, summary, sources,
owner}]`, the system's user-visible features, from its docs, config flags and CLI options (not
from the inventory, which is what they check). Aim for the features a user would name: a
scheduling policy, an offload mode, a sync mode, a protocol option. Each has one owning area. An
area models each feature it owns as a flow tagged `feature:<id>`, or skips it in
`skips/<area>.features.json` with a reason.

**Failures.** Write the profile's `failures` with the features: `[{id, summary, sources, owner,
on}]`, one row per way a shared component or edge fails (`on`: redis, the scheduler, a client
disconnect, a node death, a lease loss, an upstream provider), owned by the area whose behavior
handles it. An area models each failure it owns as a flow tagged `failure:<id>` that a scenario
runs with the failure injected (a fault, a kill, a cancel or a state change), or skips it in
`skips/<area>.failures.json`; `--failures --strict-failures` gates it (DESIGN §13.1 item 22).

**Contracts beyond the spec.** An OpenAPI file covers only what it covers; one model
dropped fields of its RPC views, the SSE terminator and usage frames, and an analytics event
body, because nothing compared them. Extract those contracts from the code into
`contracts/<topic>.yaml` (DESIGN §13.1 item 34): zod and tRPC routers (request and response
schemas, error codes), SSE emitters (`stream: {frames: [{name, schema}], terminator, order}`,
with a const in each frame's schema that tells the frames apart) and event schemas. Each
contract cites its code in `sources` and names its interface by `match`, so areas can read them
like the predeclared seams. The full gate checks them with `$CONTRACTS`.

**Entry overrides.** Path globs can't split a file whose entries belong to different areas, such
as a route table (hundreds of control-plane routes in one generated server file). For
those, add a profile `overrides` item `{file: <path or glob>, name: <entry name or glob>, area,
reason}`. `assign_inventory.py` gives an entry the override's area when both its file and its
name match (fnmatch; `name` defaults to `*`), and the override beats every `owns` glob. When
several overrides match, the most specific wins: the longest literal prefix of `name` (leading
wildcards skipped, so `* /v1/nodes/pod-*` beats `* /v1/nodes/*`), then of `file`, then the first
listed. Its output counts the entries each override assigned and lists overrides that match
nothing. `{symbol, area, reason}` overrides stay code-ownership notes for the brief.

**Test targets.** Map every test file to the code it tests, so the gates can weight the model by
the project's own tests. `test_targets.py` reads imports (Python, TypeScript, Java), follows
re-exports and small test helpers, adds the source file named like the test, and drops targets
imported by more than 10% of the tests (platform shims, loggers). It prints how many tests
resolved at least one target; expect above 90% (vLLM 96%, VS Code 100%), and add `area_globs` or
read the unresolved ones when it is lower. Go has no import resolution: a Go test targets the file
in its own directory named like it, dropping trailing name words (`admin_list_e2e_test.go` →
`admin_list.go`), then the same-directory files declaring the identifiers it uses. When tests sit
next to their code, set `oracle.colocated: true`. Otherwise every source file under `test_dirs`
counts as test code and nothing resolves (one Go build: 0% without it, 99% with it).

**Commands.**

```sh
$CHECK -f $WS/skeleton.yaml --code $CODE --strict-citations
# each test file and the code it tests -> $WS/test-targets.json, with the resolution rate per area
python3 $SCRIPTS/test_targets.py $WS
# the feature list parses, every feature has an owner (all missing until the areas build)
$CHECK -f $WS/skeleton.yaml --features $WS/profile.yaml -q
# the contract files parse (most are unmodeled until the areas build)
$CHECK -f $WS/skeleton.yaml $CONTRACTS -q
# which entries each area owns (globs plus entry overrides), to size the areas
python3 $SCRIPTS/assign_inventory.py $WS --dry-run
# before fan-out: write each entry's area into the inventory. Ownership then comes from the
# profile rather than from citations, so a boundary stub that cites the owner's code doesn't
# charge the caller for that file. Also record the profile's group skip rules as
# skips/_profile.json, so marketing, CI and tooling entries count as skipped, not unowned.
python3 $SCRIPTS/assign_inventory.py $WS
```

**Exit criteria.**
- 0 errors and 0 citation problems on the skeleton alone.
- Every inventory entry maps to exactly one area under the path rules plus `overrides`.
- Every area's entry count is within `scale.area_entries` (split or merge areas otherwise).
- The naming rules produce a predictable id for every entry kind (write one worked example per
  kind into the profile).
- The error convention lists every code, with status and `retryable`, checked against the code
  that throws.
- Each predeclared seam names its owner, and its shapes cite the owner's code.
- `features` lists the user-visible features, each with one owning area among `areas`.
- Every response, error set, stream or event body the spec doesn't cover has a contract in
  `contracts/*.yaml` that cites its code.
- `test_targets.py` resolved at least one target for 90% of the test files.

**Example.** Cassandra fixed the ConsistencyLevel enum names, `partition_key` as a string,
`token` as an integer, `timestamp` in microseconds, and exception names in kebab-case with the
native-protocol status. It did **not** predeclare `storage-proxy.read`, and 63 of the 140 merged
failures were callers guessing its request shape.

## Stage 3: Fixtures

Write the shared worlds before fan-out, so that every area tests against the same cluster, the
same schema and the same clock.

**Inputs.** The profile's `config`, `instances` and `fixtures`; the deployed config files.

**Outputs.** `fixtures.yaml`, owned by the coordinator: the `fixtures`, plus a **reference** to
each shared config. A config entity belongs to the area whose code reads it (DESIGN §13.1).

1. **Assign and reference the shared configs.** For each value in `config.required` (a timeout,
   limit, mode or feature flag that several areas read), the profile names the owning area. Put a
   reference in `fixtures.yaml`, with the id (from `naming.config`), the deployed `value` (from
   `config.sources` with role `deployed`), the code `default`, both lines in `sources`, and
   `attributes: {boundary: true, owner: <area>}`. Fixtures and every area's standalone check can
   then use the id. The owning area defines the real entity in its fragment during fan-out; the
   reference defers to it, so a corrected value never conflicts.
2. **Fixtures** for each world in `fixtures`: topology (instance names per group), clock
   (`epoch`), config overrides, and seed state (schemas, tables, accounts, rings, catalogs). Build
   them up with `extends` (for example, `base-schema`, then `three-node-rf3` extending it).
3. A smoke scenario per fixture that reads one seeded row back, so a typo in a state key fails
   now and not in every area.
4. **Shared data has one owner.** For each datum several areas touch (the text of an open
   document, the list of open windows, a cluster's ring), the profile's `shared_data` names the
   owning area and the readers. Write it into `BRIEF.md`. The owner keeps the only copy in its
   own component's state; every other area reads and writes it through the owner's interfaces,
   never through a copy of its own, and seeds it only through the owner's `<area>-seed`.

**Commands.**

```sh
$CHECK -f $WS/skeleton.yaml -f $WS/fixtures.yaml --code $CODE --strict-citations -v
$CHECK -f $WS/skeleton.yaml -f $WS/fixtures.yaml --scenario '^fixture-smoke-' --trace
```

**Exit criteria.**
- Every value in `config.required` has a reference with an owner, and its `value` and `default`
  are both cited.
- Every fixture in the profile exists, and its smoke scenario passes.
- Seed state uses only the fixed names: the keyspace, table, org or user ids that the shared
  shapes' `examples` use. Grep the skeleton's schema `examples` against fixture state keys.
- All timestamps in fixture state derive from the fixture's `clock`; no other epoch literals.
- Every entry in `shared_data` has exactly one owner, and the owner's component holds it.

**Example.** Cassandra's areas each invented a world: write-path seeded `ks1.*` and coordination
sent `shop.users`. The merged write path silently skipped unknown tables, and the scenarios still
passed (RESULTS.md, wrong claim 1). One `base-schema` fixture with `shop.users` and `shop.orders`,
named in the shared shapes' `examples`, removes the class.

## Stage 4: Fan-out

One agent per area, in parallel, each writing only its own files.

**Inputs.** `BRIEF.md`, rendered from `templates/BRIEF.md` with the profile; the skeleton; the
fixtures; the inventory.

**Outputs.** Per area: `fragments/<area>.yaml`, `notes/<area>.md`, `skips/<area>.json` and
`skips/<area>.features.json`.

**Commands** (each area agent runs these itself):

```sh
$CHECK -f $WS/skeleton.yaml -f $WS/fixtures.yaml -f $WS/fragments/<area>.yaml \
  --code $CODE --strict-citations --inventory $WS/inventory.json \
  --min-modeled 0.5 --min-substantive 0.5 --max-trivial 0.35 \
  --tests $WS/test-targets.json --min-test-reach 0.5 --features $WS/profile.yaml --strict-features \
  --behavior-coverage --no-mocks \
  --lint hollow,trivial,racy,seam-names --max-racy 0 --max-seam-names 0 -v
$CHECK -f $WS/skeleton.yaml -f $WS/fixtures.yaml -f $WS/fragments/<area>.yaml \
  --code $CODE --cite-sample 15 --seed <n>
# the coordinator refreshes areas and skips in the inventory (idempotent; areas may run it too)
python3 $SCRIPTS/assign_inventory.py $WS
```

**Exit criteria** (the area's hand-off, enforced by the coordinator):
1. 0 errors, 0 failed scenarios, 0 scenario warnings, 0 mocks.
2. `--strict-citations` passes, and two `--cite-sample 15` rounds with different seeds found no
   claim the code doesn't support.
3. No merge warning names the fragment.
4. Every inventory entry under the area is covered, or listed in `skips/<area>.json` with a reason. At
   least half of the area's unskipped entries are modeled (`--min-modeled 0.5`), not only
   registered, and at least half are **substantive** (`--min-substantive 0.5`): modeled by an
   interface whose behavior does more than return or set a field. At most 35% of the area's
   entry-citing interfaces are trivial (`--max-trivial 0.35`).
   A skip that claims another entity covers the entry names it: `"covered_by": "<kind>:<id>"`
   (for example `"interface:git-service.commit"`). `assign_inventory.py` rejects a skip whose
   `covered_by` names no entity in the merged fragments, and a reason that says "covered by"
   without the field; a rejected skip counts as uncovered.
5. `--lint hollow` has no `✗` findings. Caches, rate or concurrency limiters and metrics
   components carry kind or tag `cache`, `limiter` or `metrics` (or the tag `incidental`), so
   their bookkeeping doesn't trip the lint. Read each advisory `! hollow` warning: a write that went
   nowhere is a model bug, while a no-op or read path is fine.
6. `--behavior-coverage`: every `fail` and `if` branch of the area's behaviors runs in some
   scenario, or the notes say why not.
7. Every flow that writes state is tagged `writes`, and has a multi-step scenario that writes and
   then reads the effect back through the system's own read path (`--lint hollow` reports
   violations).
8. Every config the area reads is defined in its fragment (it owns it), or referenced with
   `attributes: {boundary: true}` when another area owns it. Behaviors read it as
   `config['<id>']`, durations included: `timeout_ms: "= config['write-request-timeout-ms']"`.
9. The area is within `scale.per_area`.
10. Stage 4b passed: every in-build oracle test is a passing scenario in the fragment, or recorded
    as `untranslatable` or `sim-gap`.
11. Shared data the area doesn't own (`shared_data`) is read through the owner's interfaces; the
    fragment holds no copy of it.
12. **Test reach** of at least 0.5 (`--min-test-reach 0.5`): half of the area's test files have a
    target file cited by an interface some scenario calls. `-v` lists the unreached tests; each
    one is either code the model should run (model it) or code below the model's level (a byte
    format, a kernel's numerics), which the notes may say.
    Reach is per file, so it can read 80% while the functions the tests call go unmodeled (vLLM
    and a gateway platform passed 2/36 and 9/45 blind oracle tests at that reach). `coverage_gaps.py <ws>
    --out-dir DIR` complements it at function level: it parses the definitions in each test's
    targets, keeps those the test names, and counts one as modeled when a citation overlaps its
    lines. It groups the rows by code owner, the area whose `owns` globs match the definition's
    file (the inventory's rule), because tests often call code another area owns (vLLM's
    kernels-ops tests call `fused_moe`, which models-layers owns). It writes `coverage-<area>.md`
    (the owned definitions any test references, how many are modeled, function-level reach, the
    top unmodeled definitions ranked by how many tests from any area reference them with the
    testing areas on each row, and the skip entries tests hit), `coverage-unowned.md` for files
    no area owns, and `coverage.json` with every row's owner and testing areas. `--by test`
    groups by the test's area instead. Every fix round gives each area its report as the ranked
    list of what to model, and routes the unowned rows.
13. **Features** (`--strict-features`): every profile feature the area owns has a flow tagged
    `feature:<id>` that a scenario runs, or an entry in `skips/<area>.features.json`
    (`[{id, reason, covered_by?}]`) with a reason that holds up: not "not modeled", "out of
    scope", "too large" or "todo", and `covered_by` naming the entity when the reason says
    "covered by".
14. **Racy and seam-names lints clean** (`--max-racy 0 --max-seam-names 0`): compare-and-set is
    an `if`, `if_absent`, `incr` or `transact`, never a read followed by a plain write; every
    field read at a seam is spelled as its writer spells it.
15. **Limiters and two-sided failures.** Rate limits, quotas, concurrency caps and back pressure
    are `limiters` keyed on what the code keys on (an IP, an org, a key, a dimension), not
    hand-rolled `state` counters. Each side of a two-sided failure the area owns is a flow tagged
    `failure:<id>:<role>` run under injection, or a skip with `{id, role, reason}`.

**Coordinator's checks while agents run.** Watch for agents reading forbidden paths (the
profile's `independence`), editing outside their files, or stubbing a seam the skeleton already
declares with a different shape.

## Stage 4b: Oracle in the build

Test-derived scenarios given to area agents **before** hand-off catch model bugs while the agent
still has the code in its head. In the VS Code build, the end-of-pipeline oracle found 28 model
bugs; most would have been caught here.

**Inputs.** The profile's `oracle`; the area's own test paths.

**Outputs.** `build-oracle/<area>.json` (written by the coordinator before launch), and scenarios
`oracle-build-<area>-<n>` in the area's own fragment, with one row per test in its notes (test,
scenario, verdict, cause).

```sh
# coordinator, before stage 4: 3 tests per area from its own paths, seeded apart from stage 6
for a in <area ids>; do python3 $SCRIPTS/sample_tests.py $WS --area $a; done
```

1. Each area agent reads `build-oracle/<area>.json` (its own file only; builders never read
   `oracle/`). The sample is drawn with `oracle.sample.build_seed` (default: the stage 6 seed plus
   1000), `oracle.sample.build_n` tests per area (default 3).
2. The agent translates each test as in stage 6: arrange → fixtures and `state`, act → `steps`,
   assert → `expect` over `result`, `state`, `steps` and `trace`. The scenarios live in its own
   fragment and run in its standalone gate.
3. Each must pass, or be recorded in the notes as `untranslatable` (what the test checks below the
   model's level) or `sim-gap` (the missing feature). A failing translation is fixed in the
   **model**, never by editing the scenario to match it.

**Exit criteria.** Every sampled test has a passing scenario or a recorded verdict, and the
fragment still passes the full gate.

## Stage 5: Reconciliation

Fragments that each pass alone rarely pass together. The coordinator merges, decides, and runs one
contract-fix round.

**Inputs.** All fragments; the merged check output.

**Outputs.** `reconcile/merged-check.txt`, `reconcile/<area>.txt` (that area's failing scenarios
and the merge warnings that name it), `RECONCILE.md` (binding decisions), the updated fragments
and skips, then `<repo>.json` and an inventory with every skip merged in.

**Commands.**

```sh
F=""; for f in $WS/fragments/*.yaml; do F="$F -f $f"; done
$CHECK -f $WS/skeleton.yaml -f $WS/fixtures.yaml $F \
  --code $CODE --strict-citations --inventory $WS/inventory.json \
  --min-modeled 0.5 --min-substantive 0.5 --max-trivial 0.35 --behavior-coverage \
  --lint hollow,trivial,racy,seam-names --max-racy 0 --max-seam-names 0 \
  --tests $WS/test-targets.json --min-test-reach 0.5 --features $WS/profile.yaml --strict-features \
  --no-mocks -v > $WS/reconcile/merged-check.txt 2>&1
# split by area: merge warnings ("! ...") name the fragment file; failing scenarios ("✗ scenario <id>")
# belong to the fragment that defines the scenario id
for f in $WS/fragments/*.yaml; do a=$(basename $f .yaml)
  { grep -E '^! ' $WS/reconcile/merged-check.txt | grep -F "fragments/$a.yaml"
    yq -r '.scenarios[].id' $f | while read s; do
      grep -A20 -E "^✗ scenario $s(:| )" $WS/reconcile/merged-check.txt | sed '/^[✓✗] scenario/{1!Q}'; done
  } > $WS/reconcile/$a.txt
done
# after the round: merge skips into the inventory (validating covered_by), regenerate the merged
# worlds from the profile and every <area>-seed, then require full coverage
python3 $SCRIPTS/assign_inventory.py $WS --worlds
$CHECK -f $WS/skeleton.yaml -f $WS/fixtures.yaml -f $WS/worlds.yaml $F --code $CODE --strict-citations \
  --inventory $WS/inventory.json --strict-coverage --min-modeled 0.5 --min-substantive 0.5 --max-trivial 0.35 \
  --tests $WS/test-targets.json --min-test-reach 0.5 --features $WS/profile.yaml --strict-features \
  --behavior-coverage --no-mocks \
  --lint hollow,trivial,racy,seam-names --max-racy 0 --max-seam-names 0 \
  --coverage-md $WS/coverage-tables.md -o $WS/<repo>.json
```

**Writing the decisions.** Group the failures by root cause and count them. For each cause, write
one decision that names the owner and the exact shape (template: `templates/RECONCILE.md`). The
standing rules: the owner's contract wins; unowned stubs get an owner and a pass-through
definition; one copy of each piece of logic; cluster or world state lives with its owner; assert
on your own calls and the outcome, not on another area's internals.

**The merged worlds.** `worlds.yaml` is generated, never hand-written, so it can't go stale (the
VS Code one missed a seed added after it was written). For each world in `fixtures.worlds` it
writes `full-<id>` (or the world's `full_id`; `full: false` leaves it out), which extends the
world, every `<area>-seed` and the areas' variants of that world, then appends
`fixtures.derived` verbatim. Benchmark, oracle and judge scenarios start from these.

**Exit criteria.** The full gate passes on the merge with `--strict-coverage`: 0 errors, 0 failed
scenarios, 0 merge warnings, 0 mocks, no failing hollow-lint findings, no fragment over
`--max-trivial` or under `--min-substantive` or `--min-test-reach`, no racy or seam-names finding,
no rejected skips, no missing
feature, and every entry covered or skipped. Each
area's standalone check still passes, apart from scenarios that now depend on another area's real
definition.

**Example.** Cassandra: 11 fragments merged to 0 validation errors and all citations resolving,
but 140 of 1,084 scenarios failed and there were 54 merge warnings. Nine decisions fixed all of
them in one round.

## Stage 6: Test oracle

The repo's own tests are an expectation source written by the people who know the code. Translate
a sample of them into scenarios against the merged model.

**Inputs.** `<repo>.json`; the profile's `oracle` (test directories, sample size, what to
exclude); `templates/ORACLE.md`.

**Outputs.** `oracle/<area>.yaml` (scenarios only) and `oracle/<area>.md` (one row per test:
test, scenario, verdict, cause).

1. Sample tests per area from `oracle.test_dirs`, seeded, at least `oracle.sample.per_area_min`
   per area, **leaving out every test stage 4b used**, so the final sample is independent of the
   build. The oracle reads the repo's tests and never runs them (DESIGN §13.1). The sample is
   **unit-weighted** (item 31): tests sitting with code their area owns (or where the language's
   convention puts it) are drawn at the repo's share of them, or at `--unit-share F`. Areas tend
   to model the request path and miss unit-level rules (rounding, job specs, startup checks);
   the sample checks those as often as the repo's own tests do. The sampling unit is a test file,
   one case each (`--unit file`), or a test function (`--unit function`: every Go `func TestX`,
   Python `def test_x`, TS/JS `it(`/`test(`, Java `@Test` in the mapped files; exclusion is then
   per test, not per file). With no `--unit`, a sample that would come back empty, or hold
   fewer than `--min-size N` tests, is redrawn by function, and the script says so on stderr.
2. For each test: its arrange step becomes fixtures and `state`; its act steps become scenario
   `steps`; its asserts become `expect`, over `result`, `state`, `steps` and `trace`.
3. Run each against the merged model, unedited.

```sh
# writes oracle/sample.json and prints the unit share achieved and the counts per area
python3 $SCRIPTS/sample_tests.py $WS --exclude-sample "$WS/build-oracle/*.json"
$CHECK -f $WS/<repo>.json -f $WS/oracle/<area>.yaml --no-mocks --lint hollow -v
$CHECK -f $WS/<repo>.json -f $WS/oracle/<area>.yaml --scenario '^oracle-<area>-' --trace
```

**Verdicts.** `pass`; `model-bug` (the model disagrees with the test and the code; cite both);
`sim-gap` (name the missing feature); `untranslatable` (the test checks something below the
model's level, such as byte layout; say what). A failure is never fixed by editing the scenario
until it matches the model.

**Exit criteria.** Every sampled test has a verdict. Every `model-bug` is filed against its owning
area as a fix. Every `sim-gap` is in the results' roadmap list.

## Stage 7: Judging

Independent judges check the model against behaviors that are well known about the system.

**Inputs.** `BENCHMARK.md`, written **before stage 4** from docs and common knowledge and never
shown to builders (`templates/BENCHMARK.md`); `judge/JUDGE.md` (`templates/JUDGE.md`); the
merged model; the code.

**Outputs.** Per group: `judge/<group>.md`, `judge/<group>.json`
(`[{case, score, cause, expectation_corrected, summary}]`), and `judge/scenarios/<case>.yaml`.

1. **Verify each expectation against the code first.** Confirm or correct it, citing code. A
   corrected expectation replaces the original. Never score against an unverified expectation.
2. **Run each case** as a scenario that uses only fixtures, inputs, `state`, `config`, `choices`,
   `faults` and `steps`. No ontology edits and no mocks.
3. **Score**: pass, partial, fail, missing, sim-gap. Every non-pass gets a root cause: model,
   contract, simulator or benchmark.
4. Spot-check faithfulness beyond the benchmark: `--cite-sample 10` on the touched flows, and the
   builders' "docs versus code" findings, confirmed or refuted.

```sh
$CHECK -f $WS/<repo>.json -f $WS/judge/scenarios/<CASE>.yaml --no-mocks -v --trace
$CHECK -f $WS/<repo>.json --code $CODE --cite-sample 10 --seed <n>
```

**Exit criteria.** Every case has a verified expectation, a score and, unless it passes, a cause
with a citation. Judges wrote only under `judge/`.

**Example.** Cassandra: 20 of the 44 expectations written from docs were wrong or imprecise for
5.0.9 (the deployed compaction default is STCS, not UCS; hint dispatch is a 10 s poll, not a
gossip event; the LWT back-off is random, not exponential). Scored against the unverified list,
a correct model would have looked wrong.

## Stage 8: Results

**Inputs.** Every stage's outputs.

**Outputs.** `RESULTS.md`:
- **the build**: entity counts, the final gate lines, coverage (covered, skipped, total), the
  behavior-coverage totals per area;
- **the oracle**: verdicts per area;
- **the benchmark**: a scorecard per group, root-cause counts, and the corrected expectations;
- **wrong claims to fix**: one row per model error, with area and citation; these go back to the
  owning area as fixes, then through the full gate again;
- **simulator gaps**, ranked by how many areas, oracle tests and judges hit each one: this is
  mosaic's roadmap input.

**Exit criteria.** Every non-pass from stages 6 and 7 appears once, either as a model fix (with
owner) or as a simulator gap. The merged model is committed only after its fixes pass the full
gate. The scores reported for the build are the blind ones of the next section.

## Blind re-measurement: the end of every round

Every build round and every fix round ends with a measure no builder saw (DESIGN §13.1 item 31).
Cases a builder fixed against stop measuring the model: a gateway platform's round 2 scored 38 of 45 on
the benchmark and 33 of 35 on the oracle it had been fixed against, then 10 of 40 and 6 of 37 on
a blind benchmark and a fresh oracle sample.

**Inputs.** The merged model after the round's fixes pass the full gate; every earlier
`BENCHMARK*.md` and `oracle*/sample.json`; `templates/BENCHMARK.md`, `templates/ORACLE.md` and
`templates/JUDGE.md`.

**Outputs.** For round n: `BENCHMARK<n>.md`, `oracle<n>/sample.json`, `oracle<n>/<area>.{yaml,md,json}`,
`judge<n>/<group>.{md,json}` and `judge<n>/scenarios/`; the round's section in `RESULTS.md`.

1. **Before the round starts**, a separate agent, one that builds and fixes nothing, writes
   `BENCHMARK<n>.md` from `templates/BENCHMARK.md`: new cases from docs and common knowledge,
   none taken from earlier benchmarks, weighted toward what earlier rounds' fixes didn't touch.
   Written before the fixes, it can't be shaped by them.
2. **When the round's fixes pass the full gate**, draw a fresh oracle sample that leaves out every
   earlier sample, unit-weighted as in stage 6. When the earlier samples have used up the test
   files, the draw switches to test functions on its own; pass `--min-size N` to keep the blind
   sample from shrinking below N.
3. **Fresh agents score both.** New oracle agents translate `oracle<n>/sample.json` (stage 6), and
   new judges score `BENCHMARK<n>.md` (stage 7), verifying each expectation against the code
   first. None of them built, fixed or judged in an earlier round.
4. **Report the blind scores as the round's scores.** Re-runs of earlier benchmarks and oracle
   samples are regression checks, reported apart and labeled as seen. Every non-pass goes back
   to its owner as a fix for the next round, which in turn ends with `BENCHMARK<n+1>.md` and
   `oracle<n+1>/`.

```sh
# round n: every earlier sample is excluded, the in-build ones included
python3 $SCRIPTS/sample_tests.py $WS --out $WS/oracle<n>/sample.json \
  --exclude-sample "$WS/build-oracle/*.json" --exclude-sample "$WS/oracle*/sample.json"
$CHECK -f $WS/<repo>.json -f $WS/oracle<n>/<area>.yaml --no-mocks --lint hollow -v
$CHECK -f $WS/<repo>.json -f $WS/judge<n>/scenarios/<CASE>.yaml --no-mocks -v --trace
```

**Independence.** Builders and fixers never read `BENCHMARK<n>.md`, `oracle<n>/` or `judge<n>/`,
of this round or any earlier one; fix briefs carry the owner's failing case restated as a model
fix with its code citation, never the benchmark or the oracle file. The benchmark agent, the
oracle agents and the judges never edit the model.

**Exit criteria.** `BENCHMARK<n>.md` predates the round's first fix; `oracle<n>/sample.json`
shares no test with any earlier sample; every case has a verified expectation and a score, every
sampled test a verdict; `RESULTS.md` reports the blind scores as the round's, with the seen
re-scores apart.

## Hierarchical runs

The stages above run at any scope (DESIGN §14). A refinement of one component is the same
pipeline run on the component's code paths, at a deeper `level`, with the parent component's
contract as an input. `mosaic compose` runs it as a workflow:
`.claude/skills/mosaic-generate/compose/ontology-pipeline.yaml`, whose `README.md` maps each stage
to this runbook. A child differs from a root run in four ways:
- **Stage 2.** The skeleton declares `refines` and one boundary interface per contract
  interface, with `implements:` and the parent's shapes. The parent's scenarios that cross the
  component are projected onto it as acceptance scenarios, which areas run with their gate.
- **Stage 4.** Where the code disagrees with the contract, areas model the code and report the
  disagreement. They never edit the contract.
- **After stage 5.** `check -f <parent> --refinement <child> --apply-timing <file>` compares boundary
  outcomes. Timing differences don't fail it; they replace the parent's latency (§14.3).
- **Stages 4b, 6 and the blind measure.** A component maps to few test files (a metering
  component: 9 files, 83 test functions), so one test per file runs out after the build oracles.
  Draw by function, and add the parent's tests that reach the scope:
  `sample_tests.py $WS --unit function --reach-from <parent>/test-targets.json` adds every parent
  test whose targets include a scope path (`inventory.scope_paths`, else the areas' `owns`, or
  `--scope-paths FILE`). Use the same flags in every draw of the run, so exclusion lines up.
- **Change requests.** Each contract disagreement becomes a change request filed against the
  parent run, for the parent's owners to decide. A child never silently disagrees.

To zoom in, list components in the run's `zoom` input (refined once the run passes its gate), or
start `compose/zoom.yaml` later as a detached child of the finished run.

**Schedule exploration and the Gomela oracle (optional).** Concurrency bugs often pass on the
simulator's default schedule. `check --explore <scenario regex> --schedules N [--jitter-ms M]`
reruns the matching scenarios (say the areas' `race` scenarios) under up to N schedules: other
tie-break orders of same-time tasks and deliveries, other orders of `parallel` branches and join
counting, and at_ms jitter of up to M ms. It skips reorderings of work on disjoint components
(DESIGN §15.5). A failing schedule is written to `.mosaic/replay/<scenario>.replay.json`
(`--replay-dir`), replacing an older one, and `check --replay <file>` reproduces it exactly. When a
scenario passes every schedule (a later round fixed the race), its replay file is stale: the check
removes it and prints `removed stale replay (passes every schedule now): <path>`. `--keep-replays`
keeps such files. Add `--scenario '^$'` to skip the ordinary runs. The UI's Exploration tab re-runs
each remaining replay against the revision it shows, so a file that passes there is stale too.

For a Go component refined to the `runtime` level, Gomela (Go to Promela, checked with SPIN) is an
independent oracle on the code itself:
`.claude/skills/mosaic-generate/scripts/gomela.sh $CODE/<package dir> [<out dir>]`. It runs only
when `gomela` and `spin` are installed. Otherwise it explains how to install them and exits 0
(`GOMELA_REQUIRED=1` makes that exit 2). It writes its models and verdicts in the output
directory (default: a new temporary directory), never in the checkout. A deadlock or
channel-safety failure it reports should match a scenario that fails under `--explore`. If no
scenario fails, file a disagreement for the area to check.

**What runs at the same time.** The workflow starts a stage as soon as its inputs exist. The
compose `README.md` draws the whole graph.
- **The benchmark** needs only the skeleton, and the area agents never read it, so it's written
  while they build.
- **After the merge gate,** these all start together: the oracle, the judges (one per benchmark
  group of at most 5 cases), the blind measure, the conformance check and the refinement link.
  The contract review follows the conformance check.
- **The blind measure** is split the same way as the judges. Fresh agents each take one group of
  `BENCHMARK1.md` (into `judge1/<group>.md`) or one area of the fresh sample (into
  `oracle1/<area>.*`). Then a short turn sums them, with the oracle totals under area `all`.
  In live runs, one agent judged all 34 blind cases and the sample in a row. That one turn took
  128 minutes, in runs of 110 to 260.

**Staging.** In both profiles, an area agent (a build or a fix) reports done only once
`.claude/skills/mosaic-generate/scripts/mcheck --stage $WS/fragments/<area>.yaml --accept` passes
(DESIGN §15.2). It runs the fragment against the other fragments as they last passed, so a broken
fragment fails its own staging and never blocks the others.

A **joint stage** is for changes that depend on each other: A's new copy needs B's, and B's
needs A's, so neither passes alone against the other's last-good copy. Stage them together with
`--stage $WS/fragments/a.yaml,$WS/fragments/b.yaml --accept` (or `--stage` twice). The run
validates both working copies against everyone else's last-good, and records both, or neither.
Use one when:
- a staged run fails, and its report suggests a stale peer (`~ suggest staging <peer> too`)
  whose working copy defines the id the failure names; rerun with the `~ try:` line;
- a contract change spans two areas (a renamed interface and its callers, a world fixture and
  the area fixtures it extends) and the coordinator routed it to both.

Don't widen a joint stage past the suggested peers, and don't use it to carry a fragment that
fails on its own: its items are listed under its name, and it gets fixed, not staged along.
Suggestions find direct dependencies only, so a joint run can suggest one more peer; add it and
rerun. A joint stage runs no slower than a single one: the merge is the same size. In a trial
with vLLM's round-5 fragments against round-4 last-good copies, staging engine-core alone
suggested five peers; that joint run suggested distributed, and the seven together passed
(1,540 scenarios). The coordinator no longer builds a scratch stage directory by hand.

**Budgets.** Each agent turn has a turn and time budget: for example 45 minutes per build, and
15 per judge. Where `claude` has no `--max-turns`, the executor enforces the turn limit itself: it
streams the session's events (`--output-format stream-json --verbose`), counts the assistant
turns, and stops the session once it passes the limit (DESIGN §15.7). A build, fix or coordinator turn that runs out is retried once, resuming from its
files. A judge or oracle agent that runs out gets a short turn to close the gap: cases it didn't
reach are scored `missing` with cause `budget`, and tests it didn't reach count as `unscored`.
Results report these gaps apart from the scores, because a gap was never measured.

**The light profile.** Use `compose/ontology-pipeline-light.yaml` for one or two files, or for a
single component that fits one to three areas and a handful of test files. It drops stages, not
just cases: 15 stages, against the full profile's 34 (DESIGN §15.7).
- **No benchmark stage.** The skeleton turn writes about 8 cases in one group and 4 to 6 blind
  ones, and draws the oracle and blind samples.
- **Reconciliation.** One coordinator turn reconciles, applies the decisions itself (there's no
  refix), merges until the merge command passes, and verifies the refinement link.
- **Judging.** One judge.
- **Blind measure.** One short turn.
- **Retries.** Coordinator turns have no retry stage. Builds keep theirs, and the judge, oracle
  and blind measure keep their gap turns.
- **Models.** A cheaper model for the inventory and the oracle translations.

Its zooms recurse into the light profile. With `zoom.yaml`, pass `profile: light`. Use the full
profile for a repo or a multi-area service, and for any score that will be reported or compared
across rounds: eight cases measure coarsely.

## Failure modes and the stage that prevents each

These all happened in the gateway-platform, Cassandra and VS Code builds. Each line names the guard.

| Failure we hit | What went wrong | Prevented by |
|---|---|---|
| **False coverage from line tolerance** | Coverage counted an entry as covered when a citation landed within a few lines of it. A citation of a neighboring method, or a class header, "covered" an entry nobody modeled. | Stage 2 naming rules make the interface name predictable, so coverage matches names, not nearby lines. The brief requires citing **the method's own lines**. Stage 1 records dense lists (enums, registries) so the tolerance stops at a neighbor's line. Stage 4 hand-off reads a sample of covered entries next to their covering entity, and stage 7 judges re-check it. `--behavior-coverage` then shows whether a covered interface's branches ever run. |
| **Stub shape guesses** | A caller declared another area's interface from its own call site. 63 of Cassandra's 140 merged failures were one guessed request (`storage-proxy.read`). | Stage 2 predeclares every visible seam in the skeleton with the owner's shapes, and fixes the shared field names. The brief makes the owner's contract win, and stubs merge by union with a warning on every scalar disagreement. Stage 5 decides each remaining seam once, for everyone. |
| **Each area invents its own seed world** | Write-path seeded `ks1.*`, coordination wrote `shop.users`. Writes to unknown tables were skipped silently, and every scenario still passed. | Stage 3 writes the shared fixtures before fan-out. The brief forbids private seeds of another area's state and requires `fixtures: [...]`. Shared shapes' `examples` use the fixture's names, so fake entry data lands in the seeded world by default. Unknown keys fail, they don't skip. |
| **Hollow scenarios** | Scenarios passed while their writes went nowhere: no state changed, or state changed but nothing checked it. | `--lint hollow` in every gate (stages 4 to 6). Write flows carry the `writes` tag, and the lint requires each to have a write-then-read multi-step scenario. Expectations assert on `state` or `trace`, not only on `result.ok`. |
| **Benchmark expectations from docs are wrong** | 20 of Cassandra's 44 expectations were wrong or imprecise for the deployed version and config. | Stage 7 verifies every expectation against code, with citations, before scoring, and records each correction. A wrong expectation is scored with cause `benchmark`, never against the model. |
| **Thin behaviors pass the coverage gates** | VS Code: an interface that cites an entry and only returns, or sets one field, counted as modeled. 512 of 2,155 entry-citing interfaces were trivial; in the thinnest area, half. The oracle then passed 1 of 31 tests in three groups. | `--lint trivial` and `--max-trivial` in every gate (stages 4 to 6); the modeled report's `substantive` count and `--min-substantive`. |
| **The oracle comes too late** | VS Code: the end-of-pipeline oracle found 28 model bugs after hand-off, when fixing them cost a round. | Stage 4b gives each area 3 of its own tests before hand-off; stage 6 draws a disjoint sample, so it still measures the model independently. |
| **Skips that claim coverage** | VS Code: 913 skips said "covered by the service interface it forwards to"; only about a fifth named an entity that exists. | A skip that claims coverage names it in `covered_by`; `assign_inventory.py` rejects a missing field or an unknown entity, and the entry counts as uncovered. |
| **Stale merged worlds** | VS Code's hand-written `worlds.yaml` missed `agents-seed`, so benchmark and oracle scenarios ran without the agents area's state. | `assign_inventory.py --worlds` generates `worlds.yaml` from the profile and every `<area>-seed` in stage 5, and again before stages 6 and 7. |
| **Two copies of one datum** | VS Code: two areas each modeled "the text" of an open document; edits through one never reached the other (judge cases E8, E9). | The profile's `shared_data` names one owner per shared datum; others read through the owner's interfaces (stage 3, the brief, stage 4 exit criterion 11). |
| **Gates measure the inventory, not the system** | vLLM: every gate passed, yet the oracle passed 2 of 19 translatable tests; its model bugs were whole features never modeled (KV connectors and offload, hybrid KV managers, structured outputs, data parallel), and scheduler-kv had 8 inventory entries. | The profile's `features`, written in stage 2, with `--features --strict-features` in every gate from stage 4; test reach (`test_targets.py`, `--tests --min-test-reach`) weights the model by the project's own tests. |
| **Scores on seen cases** | A gateway platform, round 2: 38 of 45 on the benchmark and 33 of 35 on the oracle the builders had fixed against; 10 of 40 and 6 of 37 on a blind benchmark and a fresh sample. | The blind re-measurement ends every round: a new `BENCHMARK<n>.md` written by a separate agent before the round, a fresh unit-weighted oracle sample excluding all earlier ones, fresh judges and oracle agents. The reported score is the blind one. |
| **Hand-rolled limiters, racy writes, split spellings, one-sided failures** | A gateway platform's blind round: limiters modeled as ad hoc counters (one area couldn't key by client IP), compare-and-set as read-then-write, `limitUSD` written and `limitUsd` read, and an idempotent retry counted as covered while the server ignored the key. | `limiters` in the brief; `--lint racy,seam-names` with `--max-racy 0 --max-seam-names 0` in every gate; two-sided `failures` entries (`sides`), each side covered by its owner (DESIGN §13.1 items 27 to 30). |
| **Mocks hiding seams** | A mocked or privately stubbed answer lets a scenario pass while the real owner's interface would refuse it, which is how seams survive to the merge. | Mocks are a last resort for isolating one fragment while debugging. `--no-mocks` is in every gate, and merged-model, oracle and judge scenarios may not use them. A branch that depends on another area's answer is driven through that area's real state or fixture. |

Two more that the stages guard against:
- **Code defaults instead of deployed values.** Every value a behavior reads is a config entity,
  owned by the area that reads it, with the deployed and default lines cited. Behaviors read
  `config['<id>']` everywhere, including durations (`timeout_ms`, `deadline_ms`, timers,
  `stagger_ms`, `join.need`), so a scenario's `config` override reaches them.
- **Wall-clock literals.** Stage 3 fixes the clock in fixtures. Behaviors derive every timestamp
  from `now`, and validation warns about large literals compared with `now`. (Cassandra's
  `should-hint` compared epoch milliseconds with simulator time, and refused every later hint.)

## Debugging a scenario

```sh
# one scenario, its trace, against the pieces that matter
$CHECK -f $WS/skeleton.yaml -f $WS/fixtures.yaml -f $WS/fragments/<area>.yaml \
  --scenario '^<scenario-id>$' --trace
# against the merged model, to see a seam
$CHECK -f $WS/<repo>.json --scenario '^<scenario-id>$' --trace
```

Read the trace in `seq` order (not `t`: timeouts and late parallel branches step backwards in
time). Check, in order:
1. the effective fixtures, topology, config and state: is the world the one you meant?
2. the first `call.start` whose `instance` or input is not what you expected;
3. `fault`, `retry`, `queue` and `timeout` events, and `late` marks after a join or timeout;
4. `set` events: did the write you assert on happen, on the instance you assert on?
5. warnings: a schema mismatch usually means a stub guessed a shape.

Against a running `mosaicd`, `mosaic sim run` and `POST /simulations` also take `fixtures`,
`topology`, `config` and `clock`, so you can rerun a scenario in another world without editing it.
A warning that a step's `at_ms` is in the past means the step started late. A step without
`at_ms` starts after the previous step's emits and timers finish; steps overlap only through `at_ms`
or `await: false` (DESIGN §13.1 item 14).

A failure that needs another area's fix is reported to the coordinator, not worked around.
